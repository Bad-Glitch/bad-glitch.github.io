01ليه نحتاج الهندسة العكسية

حدود اختبار الـ Black-Box

الاختبار من برّه بيلاحظ المدخلات والمخرجات بس، مش المنطق بينهم. مش بتشوف إزاي البيانات بتتعامل معاها داخليًا، ولا إزاي الحمايات اتبنت فعليًا، ومسارات الكود المخفية بتفضل مخفية.

الهندسة العكسية بتكشف: المنطق الداخلي وتدفق التحكم، روتينات التشفير وإدارة المفاتيح، الأسرار وendpoints والشهادات المضمّنة، وإزاي ضوابط الأمان شغّالة فعليًا.

إمتى الهندسة العكسية بتبقى ضرورية

الحالةالهدف

كل ده بينطبق بس على تطبيقات أنت مصرَّح لك تختبرها.

02أساسيات الهندسة العكسية

الهندسة العكسية ≠ مجرّد Decompiling

الـ Decompiling خطوة أداة بتحوّل الـ binary لكود مقروء — المخرج ده مادة خام مش فهم. الهندسة العكسية الحقيقية: إعادة بناء منطق التطبيق الداخلي، فهم إزاي البيانات بتتخزن وتتحوّل وتتبعت، ربط النتائج الـ static بالسلوك وقت الـ runtime، وتقرير إيه اللي تعدّله أو تتخطّاه أو تبلّغ عنه.

مستويات التجريد (Abstraction Levels)

Source Code (Java/Kotlin/Swift/C++) → Bytecode (مثل Dalvik/DEX) → Assembly (تعليمات CPU زي ARM) → Machine Code (تعليمات ثنائية)
اتجاه البناء: من فوق لتحت. الهندسة العكسية بتمشي المسار ده بالعكس.

كل خطوة نزول بتفقد الأسماء والبنية والتعليقات — ده "code transformation": تحويل الـ binary لصيغ مقروءة.

$ file target_app.apk

نصيحة: سجّل hash للملف (مثل sha256sum) عشان كل نتيجة ترتبط بنسخة بناء واحدة محددة.

المرحلة 2: التحليل الـ Static

$ jadx -d output_jadx target_app.apk
# يفك DEX bytecode لكود Java مقروء وموارد في output_jadx/ — الأفضل لقراءة المنطق بسرعة

$ apktool d target_app.apk -o output_apktool
# يفك الـ manifest والموارد ويفكك الكود لـ Smali في output_apktool/ — الأفضل للتعديل وإعادة البناء

نصيحة: استخدم Jadx لفهم التطبيق، وApktool لما تحتاج تعدّله.

المرحلة 3: التحليل الـ Dynamic

$ adb install target_app.apk
# يثبّت الـ APK على جهاز متصل أو emulator عبر ADB عشان تشغّله وتراقبه

$ frida -U -f com.target.app -l analysis_script.js
# يشغّل التطبيق (-f) على جهاز USB (-U) ويحقن سكريبتك (-l) لعمل hook ومراقبة السلوك

نصيحة: اجمع بين Frida hooks والتقاط الشبكة واللوجات عشان تربط السلوك بالترافيك.

06داخليات Android: DEX وART وSmali

بنية ملف DEX

الجزءالمحتوى
Headerأرقام سحرية (magic numbers) وchecksums وحجم الملف الكلي، لتحديد والتحقق من الملف
String Poolكل نص حرفي مستخدم في التطبيق: روابط، مفاتيح، رسائل، أسماء كلاسات أو دوال
Type Definitionsكل الكلاسات والأنواع الأولية اللي التطبيق بيستخدمها
Method Definitionsتعليمات الـ bytecode الفعلية، يعني منطق التطبيق

ليه ده مهم: الـ string pool بيوري القيم الـ hardcoded؛ وMethod definitions فيها المنطق اللي بتقراه في Smali.

من Dalvik لـ ART

بدءًا من Android 5.0، Google قدّمت ART (Android Runtime) بدل Dalvik. لما التطبيق يتثبّت على جهاز ART، الـ DEX bytecode بتتترجم لكود native فورًا (ahead-of-time).

النتيجةالتفسير
Static analysis بيبقى أفعّلكود مترجَم مسبقًا وقابل للتنبؤ أسهل في التحليل offline
هجمات الـ runtime بتصعبمفيش JIT compiler وقت التثبيت، فمفيش حاجة كتير تُستغل

ملاحظة: من Android 7.0، ART بتجمع بين AOT وJIT وcompilation موجّه بالـ profile، فمخاطر الـ JIT لسه موجودة.

JIT مقابل AOT: مقايضات أمنية

JIT — متجهات هجومAOT — مقايضات
فساد الـ code cache المترجَمتعقيد أقل وقت التشغيل = أجزاء أقل للاستغلال
JIT spray: توليد كود يمكن التنبؤ به يُستغل لـ ROP gadgetsتخطيطات ذاكرة يمكن التنبؤ بها — ممكن تساعد في تطوير استغلال
تعديل كود ديناميكي (code-patching)فعالية static analysis أعلى — المدافع كمان بيلاقي الثغرات أسهل

الخلاصة: الـ AOT بيبادل سطح هجوم الـ runtime بقابلية التنبؤ، وده بيفيد المهاجم والمدافع مع بعض.

Smali: لغة Dalvik

تمثيل مقروء لبايت كود Dalvik، الجسر بين كود Java المصدري وDEX bytecode، وأساسي للهندسة العكسية وتحليل الـ malware على Android.

التسجيلالوصف
v0, v1, v2...Local registers
p0, p1, p2...Parameter registers
thisمرجع للكائن الحالي — في الدوال غير الثابتة، p0 بيحمل this

فئات تعليمات Smali

move v0, v1              # نسخ v1 لـ v0
move-object v0, v1        # نسخ مرجع كائن
move-result v0            # تخزين قيمة مرجوعة من دالة (بعد invoke مباشرة)
add-int v0, v1, v2        # حسابي: v0 = v1 + v2
mul-int/lit8 v0, v1, 0x5  # حسابي: v0 = v1 * 5

move-result دايمًا بتيجي بعد تعليمة invoke بترجّع قيمة.

تشريح استدعاء دالة

invoke-virtual {v0, v1}, Ljava/lang/String;->equals(Ljava/lang/Object;)Z
الجزءالمعنى
invoke-virtualنوع النداء: استدعاء دالة virtual عادية
{v0, v1}registers الوسائط: v0 الكائن، v1 الوسيطة
Ljava/lang/String;الكلاس المالك للدالة (java.lang.String)
->equalsاسم الدالة المستدعاة
(Ljava/lang/Object;)Zأنواع الوسائط بالقوس، وZ تعني ترجع boolean

يُقرأ كـ Java: v0.equals(v1). تعليمة move-result التالية بتاخد الـ boolean.

الشروط في Smali

if-eq v0, v1, :cond_equal     # if (v0 == v1) goto :cond_equal
if-ne v0, v1, :cond_not_equal # if (v0 != v1) goto :cond_not_equal
if-lt v0, v1, :cond_less      # if (v0 < v1) goto :cond_less
if-eqz v0, :cond_zero         # if (v0 == 0) goto :cond_zero

بنية الـ Loops مبنية من نفس الشروط زائد goto بيرجع لـ label سابق.

إيه اللي تدوّر عليه في Smali

  • invoke-*: نداءات الدوال، خصوصًا دوال التشفير. const-string: قيم hardcoded زي مفاتيح وروابط وtokens وflags. if-*: منطق التحقق (login، ترخيص، كشف root، pinning). return-*: التلاعب بتدفق التحكم — تغيير إيه اللي الدالة بترجّعه ممكن يقلب نتيجة فحص كامل.

07داخليات iOS: Objective-C وSwift وMach-O

Objective-C: كل حاجة عبارة عن رسالة

كل حاجة في Objective-C بتحصل عبر message passing: objc_msgSend. نداء زي [obj doThing] بيتحوّل لـ objc_msgSend(obj, selector)، يتم حلّه وقت الـ runtime.

  • Method swizzling: بيسمح باستبدال تنفيذ الدوال وقت التشغيل. Category injection: بيسمح بحقن كود وقت التشغيل. ISA pointer corruption: ممكن يعيد توجيه نداءات الدوال لكود مختلف. KVO/KVC bypasses: ممكن توصل لخصائص خاصة.

Swift: إيه اللي بيتغير أمنيًا

بيصعّب هجماتبيفتح فرص جديدة
Type safety: بتمنع كتير من مشاكل فساد الذاكرةالتلاعب بجداول witness البروتوكول
ARC: بتقلل ثغرات use-after-freeهجمات type confusion عامة
Value semantics: بتحد من مشاركة الحالة القابلة للتغييرفساد البيانات الوصفية (metadata) لعمل type confusion

الـ ABI الثابت لـ Swift بيخلّي البيانات الوصفية دي يمكن التنبؤ بها وتحليلها. الخلاصة: ميزات اللغة الأكثر أمانًا بتنقل الهجمات من أخطاء الذاكرة الكلاسيكية لـ type/metadata confusion.

تشفير XOR: إيه اللي بيحصل

XOR بيقلب كل bit في النص الصريح باستخدام الـ bit المقابل في المفتاح.

Plaintext (A): 01000001
Key:           01001010
Encrypted:     00001011   (XOR بت-ببت)

خاصية المفتاح: XOR متماثل — تشفير الـ ciphertext بنفس المفتاح بيرجّع النص الصريح، وده بالظبط إزاي فك التشفير بيشتغل.

تقنيات تعتيم تدفق التحكم

  • Opaque Predicates: شروط دايمًا بتدّي نفس النتيجة، لكن بتبان معتمدة على بيانات للقارئ أو الـ decompiler. Dead Code Insertion: كود غير قابل للوصول أو بلا معنى مخلوط عشان يضيّع وقت المحلل ويلخبط الأدوات الآلية. Exception-Based Control Flow: استخدام try/catch لإعادة توجيه التنفيذ بطرق تخفي تدفق التحكم الحقيقي. Reflection-Based Obfuscation: استدعاء الدوال بالاسم وقت التشغيل بدل مباشرة، يخفي النداء من الـ static analysis.

التعتيم بالـ Reflection: قبل وبعد

// نداء مباشر — ظاهر لأي decompiler
myObject.sensitiveMethod();

// نداء بالـ reflection — اسم الدالة عمره ما يظهر كنداء مباشر
Class<?> clazz = Class.forName("com.example.MyClass");
Method method = clazz.getDeclaredMethod("sensitiveMethod");
method.invoke(myObject);

اكتشاف تعتيم الـ Reflection

الـ static analysis مستحيل تتبع نداء ما بتشوفهوش مباشرة. دوّر على التلاتة دول مع بعض: Class.forName()، getDeclaredMethod()، method.invoke().

// مزدوج الطبقة: Base64 + reflection يخفي httpClient.sendUserData(userData)
String className = decrypt("aHR0cENsaWVudA==");
String methodName = decrypt("c2VuZFVzZXJEYXRh");
Class<?> clazz = httpClient.getClass();
Method method = clazz.getDeclaredMethod(methodName, String.class);
method.invoke(httpClient, userData);

قاعدة عامة: لما تشوف التلاتة نداءات دول مع بعض، الهدف الحقيقي غالبًا نص مفكوك أو مفكّك تشفيره جنبهم.

تقنيات حماية متقدّمة

  • Packing & Compression: ضغط أو تشفير الـ binary كله؛ بيفك نفسه في الذاكرة بس وقت التشغيل. Symbol Stripping: استبدال الأسماء ذات المعنى بأسماء بلا معنى، مثل validatePassword → func_234.

ما يعتمد عليه المحللون (Pattern Recognition)

  • Cross-referencing: ربط دوال بلا اسم بسلوك مكتبة معروف. Entropy analysis: مناطق عالية الـ entropy بتوحي ببيانات معبّأة أو مشفّرة. Data flow analysis: تتبّع القيم حتى لما الأسماء تختفي. Runtime monitoring & memory dumping: ملاحظة السلوك الحقيقي واسترجاع كود مفكوك أو مفاتيح من الذاكرة.

12كسر التشفير الضعيف وفكّ التعتيم

كسر XOR الضعيف: هجوم بالنص الصريح المعروف

لو التطبيق دايمًا بيعمل XOR بنفس المفتاح، وتقدر تخمّن جزء من النص الصريح، تقدر تسترجع المفتاح.

Known plaintext: "https://"
Encrypted data:  "AQU6AuLW"
# استرجاع المفتاح: XOR النص الصريح المعروف مع بايتات الـ ciphertext المقابلة = المفتاح، قابل لإعادة الاستخدام لفك كل حاجة تانية بيحميها

إعادة استخدام المفتاح مع نص صريح معروف هو أشيع ضعف في تشفير الموبايل المحلي الصنع. تاريخيًا، نفس الفكرة كسرت ترافيك Enigma في الحرب العالمية الثانية: نص صريح معروف أو قابل للتخمين كشف الـ key stream.

التحليل الإحصائي لـ Repeating-Key XOR

  • XOR بمفتاح متكرر بيحافظ على بعض الخواص الإحصائية للنص الصريح. بايتات متطابقة في النص الصريح بمواضع i وi+keylength بتطلع بايتات ciphertext متطابقة.
  • تحديد طول المفتاح: جرّب أطوال مفاتيح مرشّحة مختلفة ضد الـ ciphertext، ودوّر على أنماط متكررة عند كل طول — معدل تطابق أعلى عند طول معيّن بيوحي إنه الطول الصحيح.

سيناريو هجوم: اختراق الجسر

1. Inject: المهاجم بيحقن JavaScript عبر XSS أو WebView مخترق
2. Call the bridge: السكريبت المحقون بينادي الجسر الـ native مباشرة من سياق الويب
3. Reach native storage: نداء الجسر بيوصل لبيانات المفروض native-only

ليه ده بيشتغل: الجسر اتبنى عشان يسمح لـ JS موثوق يوصل لبيانات native — مش قادر يفرّق بين كود موثوق وكود محقون.

الأهداف الأساسية

  • بيانات شخصية (جهات اتصال، صور، رسائل، ملفات خاصة). اعتمادات (باسوردات محفوظة، session tokens، أسرار مصادقة). معلومات الجهاز (IMEI، إصدار النظام، تطبيقات مثبّتة، بيانات بصمة). بيانات الشركة (إيميل العمل، مستندات داخلية، وصول لأنظمة الشركة عبر الجهاز).

قدرات المراقبة

  • تسجيل صوتي (التقاط صوت محيط وتسجيل مكالمات، غالبًا من غير أي مؤشر ظاهر). التقاط فيديو (الوصول للكاميرا وتسجيل الشاشة). تتبّع الموقع (GPS وأبراج الخلوي وWi-Fi). مراقبة الاتصالات (قراءة SMS وتطبيقات المراسلة والإيميل). تسجيل ضربات المفاتيح (التقاط الباسورد والنص وهو بيتكتب، حتى برّه التطبيق الخبيث).

تقنيات الاحتيال المالي

  • Banking Trojans: هجمات overlay برسم شاشة login مزيفة فوق تطبيق بنكي حقيقي لسرقة الاعتمادات. SMS Interception: قراءة SMS الواردة للقبض على OTP وتخطّي الـ 2FA. Cryptocurrency Theft: سرقة اعتمادات المحفظة وseed phrases لتفريغ محافظ العملة المشفّرة. Premium Service Fraud: اشتراك صامت في خدمات مميزة أو رسوم غير مصرَّح بيها.

التوزيع: متجهات قائمة على التطبيقات

  • تطبيقات خبيثة (أدوات أو ألعاب مزيفة مبنية لتبدو مفيدة). تطبيقات شرعية معاد تعبئتها بكود خبيث. اختراق حساب مطوّر (نشر malware عبر حساب مطوّر شرعي وثقته القائمة). تسميم التحديثات (تطبيق شرعي بيشحن تحديث خبيث بعد بناء ثقة بنسخ نظيفة).

القاسم المشترك: الهندسة الاجتماعية — كل متجه بيعتمد على إن الضحية يثق في حاجة بتبان شرعية.

التوزيع: متجهات فيزيائية وشبكية

  • USB Charging Stations ("Juice Jacking"): منفذ شحن عام بيشتغل كمان كاتصال بيانات بيثبّت malware. QR Codes خبيثة: مسح كود QR بيشغّل تحميل APK مباشر بدل الرابط المتوقع. Bluetooth Exploitation: هجمات زي BlueBorne بتخترق الجهاز من غير أي إقران. Wi-Fi Network Attacks: captive portal على hotspot خبيث لتوزيع malware متنكّر كخطوة تسجيل دخول.

هجمات سلسلة الإمداد

  • مكتبات طرف تالت (SDKs وframeworks خبيثة مسحوبة جوه تطبيقات شرعية). أدوات تطوير (بيئات تطوير مخترقة بتحقن كود خبيث وقت البناء). شبكات توزيع (اختراق CDN بيبدّل تطبيق أو تحديث نظيف بواحد خبيث أثناء النقل). تثبيت مسبق على الهاردوير (malware مثبّت من المصنع قبل وصول الجهاز للمستخدم).

إرشادات عملية لتحليل Malware

تحليل الـ malware أسهل لما تعرف بتدوّر على إيه. استخدم كل حاجة في الكورس ده — الأهداف وطرق التسريب ومتجهات التوزيع — كـ checklist. تدرّب على عينات حقيقية (راجع androzoo.uni.lu). توقّع تقنيات مكافحة التحليل (العينات ممكن تكتشف وتقاوم بيئة التحليل بتاعتك). اجمع بين الـ static والـ dynamic analysis (ولا واحدة لوحدها بتحكي القصة كاملة). استمر في التعلّم (تقنيات malware الموبايل بتتطور باستمرار).

  • طرق إدخال خاصة بالتلفزيون: الريموت والإدخال الصوتي بيضيفوا منطق تعامل مع المدخلات مش موجود في الهواتف. واجهات تحكم HDMI-CEC: بتسمح لأجهزة HDMI متصلة ببعت أوامر تحكم للتلفزيون — قناة كتير تطبيقات ما بتتوقعهاش. بروتوكولات Cast/Screen Mirroring: بروتوكولات بتقبل stream أو أوامر تحكم من أجهزة تانية على الشبكة. معالجة إشارة البث والـ Tuner: بتحلل مدخل البث والـ tuner، سطح مالوش مثيل في الهاتف.

16التطوير الآمن وDevSecOps

ليه DevSecOps الموبايل مختلف

  • توزيع عبر الـ Stores: التطبيقات بتتوزع عبر متاجر بمراجعة، مش زي تطبيق ويب تتحكم فيه كامل. مفيش نشر فوري: التحديثات ما ينفعش تتدفع فورًا زي الـ backend. تحديث مستخدمين متأخر: المستخدمين ممكن ما يحدّثوش فورًا، فتفضل نسخ قديمة معرّضة منتشرة. أجهزة غير متحكَّم فيها: مشاكل الأمان في التطبيقات المنشورة بتأثر على أجهزة مش تحت سيطرتك.

المبدأ 1: عمرك ما تثق في الـ Client

القاعدة: دايمًا طبّق تحقق server-side، حتى للفحوصات اللي التطبيق أصلًا بيعملها. التطبيق لازم يبعت معرّفات بس (زي itemId) — عمره ما يبعت قيم حساسة زي الأسعار أو الصلاحيات أو قرارات منطق العمل. ليه: أي حاجة متحسوبة أو متقرر على الـ client ممكن تتعترض أو تتعدّل أو تتعاد — السيرفر هو الوحيد اللي يقدر يفرض القرار.

المبدأ 2: التحقق من المدخلات خط دفاعك الأول

  • Format Validation: هل البيانات بالصيغة المتوقعة (النوع والطول والبنية الصح)؟ Range Validation: هل البيانات جوه الحدود المقبولة (كمية أو مبلغ)؟ Business Logic Validation: هل البيانات دي منطقية في سياق تطبيقك، مش بس شكلها صح؟

التلاتة كلهم، كل مرة: بيانات ممكن تكون بالصيغة الصح وجوه المدى ولسه ما لهاش معنى لمنطق العمل — كل طبقة بتمسك إيه اللي التانية بتفوّته.

المبدأ 3: قنوات اتصال آمنة

بدل ما تثق في أي Certificate Authority، تضمّن بصمة شهادة سيرفرك مباشرة جوه تطبيق الموبايل — ده هو الـ Certificate Pinning: التطبيق بيثق بس في الشهادة الواحدة اللي اتبنى على توقّعها.

من غير Pinningمع Pinning
التطبيق بيثق في أي شهادة موقّعة من CA موثوق — شهادة متاحة بغلط أو حصل عليها المهاجم تقدر تعترض الترافيكالـ MITM محتاج بالظبط الشهادة أو المفتاح المثبّت — شهادة صحيحة من أي CA تاني مرفوضة

المرحلة 1: فحوصات أمان وقت الـ Commit

# فحص أسرار hardcoded
grep -r "api_key\|password\|secret" src

# فحص صلاحيات خطرة في الـ manifest

بتمسك: أسرار وصلاحيات واسعة جدًا اتعمّلها commit بالغلط، قبل ما توصل لأي بناء. هدف المرحلة: مسك أرخص وأشيع الأخطاء بأسرع وأوتوماتيكي طريقة ممكنة.

المرحلة 2: التحقق الأمني وقت البناء

  • فحص ثغرات الاعتماديات (كل مكتبة التطبيق بيسحبها). فشل البناء لو اتلاقت ثغرات حرجة (البناء بيتوقف، مش بس بيحذّر). تحليل أمان آلي على الـ APK المبني نفسه، مش بس الكود المصدري. التحقق من التوقيع قبل ما يتقدّم.

المرحلة 3: اختبار أمان ما قبل الإنتاج

إيه اللي بيتختبر: endpoints الـ API عن ثغرات شائعة، أمان الـ API العام، أمان تطبيق الموبايل العام، تخطّي المصادقة، عيوب التفويض. المعيار المرجعي: استخدم OWASP MASVS ودليله MASTG لتنظيم المرحلة دي — checklist قابل للتكرار ما يعتمدش على ذاكرة شخص واحد.

المرحلة 4: مراقبة أمنية مستمرة

المراقبة الأمنية وقت الـ runtime بتعيش جوه التطبيق المشحون نفسه، مش بس في لوجات الـ backend. راقب محاولات العبث (كشف تعديل في الـ binary أو الـ runtime). راقب أنماط استخدام الـ API (إساءة استخدام أو أتمتة ما بتبانش زي مستخدم حقيقي). راقب محاولات الـ debugging (debugger متصل أو إطار instrumentation). افحص وضع أمان الجهاز (هل الجهاز نفسه rooted أو jailbroken أو مخترق).

قواعد Static Analysis الخاصة بـ Android

  • كشف exported activities من غير فحص صلاحيات. فحص intent handling غير آمن (implicit intents بتحمل بيانات حساسة). تحديد تحقق SSL غير صحيح. فحص صلاحيات ملفات غير كافية. كشف استخدام shared preferences غير آمن. فحص debug flags متروكة مفعّلة في بناء الإنتاج.

قواعد Static Analysis الخاصة بـ iOS

  • تحديد استخدام Keychain غير آمن. كشف تعامل URL scheme غير صحيح. فحص تعطيل ATS. فحص تضمين backup غير آمن. كشف logging لمعلومات حساسة. فحص تنفيذ مصادقة بيومترية غير صحيح.

قواعد Static Analysis عبر المنصات

  • مفاتيح وباسوردات تشفير hardcoded. خوارزميات تشفير ضعيفة (MD5, SHA1, DES). توليد أرقام عشوائية غير آمن. ثغرات SQL injection في قواعد بيانات محلية. أنماط اتصال شبكة غير آمنة.

دمج Static Analysis في سير العمل

  • تكامل الـ IDE (يمسك المشاكل قبل حتى ما تتعمل commit). Pre-Commit Hooks (تمنع كود معرّض من دخول الـ codebase أصلًا). تكامل Pull Request (يوفّر سياق مراجعة أمنية مباشرة لمراجعي الكود). تكامل خط أنابيب البناء (يضمن إن مفيش ثغرة تفلت بغض النظر عما فاتته الخطوات السابقة).

آليات الدفاع ضد الـ AI الخصومية

  • Adversarial Training: تدريب نموذج الكشف على الأمثلة الخصومية نفسها عشان يتعلم يقاومها. Model Ensemble Diversity: استخدام نماذج متعددة مبنية بطرق مختلفة، فمفيش خدعة خصومية واحدة تخدعهم كلهم. Federated Learning: تدريب عبر أجهزة كتير من غير تمركز البيانات الخام، بيحسّن الكشف مع الحفاظ على الخصوصية.

Voice with Emotional Context (مصادقة صوتية بتاخد في الاعتبار النبرة العاطفية كمان). Eye Movement Tracking (استخدام أنماط الانتباه والنظر كإشارة سلوكية إضافية).

أنظمة المصادقة المستمرة

  • تسجيل خطر قائم على المخاطر باستمرار بدل لحظة نجاح/فشل واحدة. دمج بيومتري متعدد الأنماط (دمج إشارات بيومترية متعددة لقرار أقوى وأصعب تزويرًا). محفّزات واعية بالسياق (إعادة مصادقة بس لما السياق يتغيّر بشكل ملموس — موقع جديد، شبكة جديدة، سلوك جديد). قوالب حافظة للخصوصية (تخزين قوالب بيومترية بشكل يتحقق من الهوية من غير كشف البيانات البيومترية الخام).

التشفير ما بعد الكمّي على الموبايل: التكلفة العملية

  • تبعات حجم المفتاح (خوارزميات ما بعد الكمّي غالبًا محتاجة مفاتيح أكبر، بتبعات تخزين حقيقية على الموبايل). عبء حسابي (رياضيات أكتر تطلبًا تعني شغل CPU أكتر من التشفير الكلاسيكي). تأثير عمر البطارية (عمليات تشفير أثقل بتستهلك طاقة أكتر، مقايضة مباشرة لعمر البطارية). عرض نطاق الشبكة (مفاتيح وتوقيعات أكبر تعني بيانات أكتر مرسلة على الشبكة لنفس العملية).

أمان ألعاب الموبايل: تهديدات خاصة بالمعمارية

  • اعتراض وتلاعب بـ stream اللعبة. هجمات توقيت قائمة على الـ latency (استغلال توقيت يمكن التنبؤ به لميزة غير عادلة). تلاعب بحفظ اللعبة على السحابة بدل الجهاز. استغلال تأخّر الإدخال (input lag) للغش التنافسي.

أمان ألعاب الموبايل: الدفاعات

  • تشفير كامل للـ stream (End-to-End). تحقق من المدخلات مبكرًا قدر الإمكان لمسك أفعال غير صالحة واضحة. مزامنة حالة آمنة (الحفاظ على حالة اللعبة متسقة ومتحقق منها بين الـ client والسيرفر). تكامل نظام anti-cheat مخصص.

5G: أسطح هجوم جديدة

  • ثغرات تقسيم الشبكة (Network Slicing) — شرائح 5G منفصلة منطقيًا ممكن ما تكونش معزولة بقد ما مفترَض. فجوات أمان Edge Computing — المعالجة الأقرب للمستخدم بتقرّب وتوسّع سطح الهجوم كمان. إدارة أجهزة IoT الضخمة على مقياس 5G. latency فائقة الانخفاض مقابل الأمان — متطلبات أداء ممكن تغري الفرق بقطع زوايا أمنية.

تحسينات أمان 5G

  • بروتوكولات مصادقة معزّزة (معمارية أمان 5G الخاصة في 3GPP TS 33.501). أمان افتراضية وظائف الشبكة. حوسبة Edge متعددة الوصول آمنة. خدمات موقع حافظة للخصوصية (تصميم ميزات موقع تقلل ما بتكشفه عن المستخدم).

Blockchain وWeb3 على الموبايل: مخاطر

  • ثغرات العقود الذكية اللي واجهة موبايل بتتعامل معاها. إدارة مفاتيح خاصة على الموبايل (الجهاز بيبقى حارس مفاتيح، ولو ضاعت أو اتسرقت يعني فقدان كامل للأموال). أمان الجسور عبر السلاسل (هدف متكرر وعالي القيمة). هجمات MEV عبر تطبيقات الموبايل.

Blockchain وWeb3: أطر أمان

  • دمج Hardware Security Module (هاردوير مخصص لحماية المفاتيح الخاصة، مش تخزين على مستوى التطبيق بس). تنفيذات محافظ متعددة التوقيع (موافقات متعددة مطلوبة للمعاملة). إدارة هوية لامركزية (المستخدمين بيتحكموا في بيانات هويتهم من غير سلطة مركزية). تطبيقات Zero-Knowledge Proof (إثبات حقيقة حاجة من غير كشف البيانات الأساسية).

Zero Trust للموبايل: مبادئ أساسية

  • عمرك ما تثق، دايمًا تحقق (مفيش جهاز أو مستخدم أو تطبيق موثوق افتراضيًا). افتراض الاختراق (صمّم كأن مهاجم موجود بالفعل جوه، لتحديد إيه اللي اختراق واحد يقدر يوصله). أقل صلاحية ممكنة. مراقبة وتحقق مستمر (الثقة عمرها ما دائمة — بتتقيّم باستمرار مش بس وقت الـ login). (مرجع: NIST SP 800-207)

Zero Trust: تكييفات خاصة بالموبايل

  • تصديق صحة الجهاز (التحقق من وضع أمان الجهاز نفسه قبل الثقة بأي حاجة بيبعتها). خطوط أساس سلوك التطبيق. تقسيم شبكة دقيق (micro-segmentation بيحدد الحركة الجانبية حتى بعد الاختراق). سياسات أمان محورها الهوية.

Zero Trust: مكوّنات المعمارية

  • درجات ثقة جهاز الموبايل (محدّثة باستمرار). سياسات وصول شرطية (تتكيف مع الموقع وحالة الجهاز والسلوك). أمان API Gateway (نقطة تفتيش واحدة منفَّذة لكل نداء API). وصول شبكة مجزّأ بدقة.

Zero Trust: تحديات التكامل

  • توازن تجربة المستخدم (التحقق المستمر ما ينفعش يبقى احتكاك دائم للمستخدمين الشرعيين). تقليل تأثير الأداء (كل فحص إضافي له تكلفة، لازم يفضل سريع بما يكفي ليكون غير مرئي). توافق التطبيقات القديمة (تطبيقات قديمة ما اتبنتش بفكرة zero trust لسه محتاجة تشتغل). التعامل مع سيناريوهات الـ Offline.

18دراسات حالة واقعية

Pegasus — برمجية تجسس

spyware بيجاسوس من NSO Group، اتكشف لأول مرة علنًا سنة 2016 عن طريق Citizen Lab وLookout، استخدم 3 ثغرات iOS من نوع zero-day بالاسم المستعار "Trident" (CVE-2016-4655, -4656, -4657) لاختراق الهواتف المستهدَفة بصمت، في بعض الحالات من غير أي تفاعل من الضحية خالص.

بعد التثبيت، قدر يقرا الرسائل، يتتبّع الموقع، يفعّل المايكروفون والكاميرا، ويسرّب البيانات — تقريبًا كل قدرة مراقبة اتغطت، منفَّذة مع بعض ضد هدف واحد عالي القيمة.

الدرس: حملات التجسس المستهدَفة بتبرر عمق الـ forensics وتحليل الـ runtime — الاختراق ممكن يكون غير مرئي للضحية ويسيب آثار خفيفة بس.

XcodeGhost — سلسلة إمداد

سنة 2015، مطوّرين في الصين حمّلوا نسخة مزيفة مليانة malware من Xcode بتاع Apple من mirror محلي، أسرع من سيرفرات Apple نفسها. الأداة المخترَقة حقنت كود خبيث بصمت جوه كل تطبيق بنته.

حوالي 4000 تطبيق iOS اتشحنوا على الـ App Store الرسمي حاملين الكود المحقون ده، بما فيهم تطبيقات مشهورة جدًا — الاختراق حصل على مستوى أداة التطوير، مش كود التطبيق نفسه.

الدرس: compiler أو أداة بناء مخترَقة بتسمّم كل حاجة بتلمسها — التحقق من سلسلة أدواتك مهم زي مراجعة كودك.

Triada — تثبيت مسبق على الهاردوير

Triada، اتكشف سنة 2016 ولاحقًا اتلاقى مضمّن في firmware بعض أجهزة Android الاقتصادية، كان حصان طروادة متطور بوصول modular على مستوى root مخبوز قبل ما الهاتف حتى يوصل لرف المتجر.

اشتغل أغلبه في الذاكرة، بيعدّل عمليات النظام مباشرة ويمنح modules خبيثة تانية وصول عميق — دفاعات وقت التثبيت وفحص المتجر عمرها ما كان عندها فرصة، لأن الجهاز نفسه كان أصلًا مخترَق.

الدرس: هجمات التثبيت المسبق على الهاردوير بتهزم كل فحص متجر وruntime — أصل الجهاز مهم زي أصل التطبيق.

FluBot — هندسة اجتماعية وتوزيع

FluBot انتشر عبر أوروبا خلال 2021 برسائل SMS بتتنكّر كإشعارات توصيل طرود، بتقنع الضحايا يثبّتوا تطبيق تتبّع مزيف كان فعليًا malware بنكي لـ Android.

كل هاتف مصاب كان بيبعت تلقائيًا نفس رسالة الطعم لجهات اتصال الضحية، بيدّي للدودة انتشار ذاتي متفجّر لحد ما عمليات بقيادة Europol عطّلت بنيته التحتية سنة 2022.

الدرس: طعم مقنع واحد، مع قائمة اتصال الضحية نفسها كقناة توزيع، يقدر يتفوّق على أي دفاع مراجعة متجر تقريبًا.

Judy وتطبيقات احتيال الإعلانات

سنة 2017، الباحثين لقوا عائلة تطبيقات Android — أغلبها ألعاب بسيطة — على الـ Play Store الرسمي، اتثبّتت تقديريًا عشرات الملايين من المرات، كانت بتولّد نقرات إعلانات احتيالية بصمت.

التطبيقات عدّت مراجعة المتجر الأولية بالتصرف الطبيعي في البداية، وبعدين بتجيب payload خبيث بعد التثبيت لتنفيذ سلوك احتيال الإعلانات، برّه نظر المراجعين والمستخدمين.

الدرس: "متجر رسمي" مش نفس حاجة "آمن" — payloads متأخرة أو مجلوبة عن بُعد مبنية خصيصًا للإفلات من المراجعة.

Goldoson SDK — سلسلة إمداد عبر مكتبة

سنة 2023، باحثو أمان حددوا SDK ثالث خبيث لـ Android، اتسمى لاحقًا Goldoson، مضمّن جوه عشرات التطبيقات الشرعية اللي اتحمّلت مجتمعة أكتر من 100 مليون مرة.

مطوّرو التطبيقات كانوا ضمّنوا الـ SDK لوظيفة إعلانات أو أداة شرعية، من غير ما يعرفوا إنه كمان بيجمع بيانات عن التطبيقات المثبّتة وأجهزة Wi-Fi وBluetooth القريبة، وبيرتكب احتيال إعلانات بهدوء في الخلفية.

الدرس: كل SDK طرف تالت هو كود بتشحنه لمستخدميك — تدقيق الاعتماديات مهم زي تدقيق كودك الخاص.

BlueBorne — استغلال Bluetooth

اتكشف من Armis Labs سنة 2017، BlueBorne كان سلسلة ثغرات في تنفيذات Bluetooth أثّرت على مليارات أجهزة Android وiOS وWindows وLinux — بما فيها هواتف كتير.

مهاجم جوه مدى Bluetooth قدر يخترق جهاز من غير إقران ومن غير أي تفاعل مستخدم خالص، بمجرد ما البلوتوث يكون مفعّل، وبعدين ينتشر لأجهزة قريبة تانية معرّضة.

الدرس: بروتوكول ما حد بيفكر فيه ممكن يبقى متجه اختراق كامل — هجمات قائمة على القرب تستحق نفس الفحص زي القائمة على الشبكة.

أبحاث Juice Jacking العامة

باحثو أمان أثبتوا مرارًا في مؤتمرات زي DEF CON إن محطة شحن USB عامة معدَّلة تقدر تثبّت malware أو تسرّب بيانات من هاتف جاي بس عشان يشحن بصمت.

الهجوم بيشتغل لأن كابل USB العادي بيحمل طاقة وبيانات مع بعض — منفذ شحن خبيث يقدر يكلّم واجهة بيانات الهاتف لحظة ما يتوصّل، من غير أي علامة ظاهرة للمستخدم.

الدرس: بنية الشحن الفيزيائية جزء من سطح هجوم الموبايل — الحل (كابل طاقة بس أو USB data blocker) بسيط، بس لو الناس عارفة تستخدمه.

أسرار Hardcoded على نطاق واسع

مسوحات بحثية مستقلة متعددة لتطبيقات على Google Play وApple App Store، عبر عدة سنين، لقت مرارًا آلاف التطبيقات المنشورة بتشحن مفاتيح تخزين سحابي أو API أو قاعدة بيانات hardcoded.

الباحثين ببساطة عملوا decompile لـ APKs متاحة عامة ودوّروا في الـ strings والموارد المستخرَجة عن أنماط تطابق صيغ مفاتيح واعتمادات معروفة — بالظبط منهج الـ static analysis.

الدرس: ده النمط المضاد "الأسرار الـ Hardcoded" على نطاق هائل — فحص أسرار آلي في الـ CI كان هيمسك تقريبًا كل الحالات دي قبل النشر.

Cerberus وعائلة Banking Trojans

Cerberus، وعائلة الـ malware المرتبطة Anubis وAlien، انتشروا خلال 2019-2020 كـ banking trojans لـ Android بتتباع كخدمة (malware-as-a-service)، بيدّوا لمشترين قليلي المهارة عدة هجوم overlay جاهزة.

بعد التثبيت، الـ malware كان بيراقب لحد ما الضحية يفتح تطبيق بنكي حقيقي، وبعدين يرسم فورًا شاشة login مزيفة مطابقة بكسل فوقه، مع اعتراض SMS OTP اللازم لإكمال تحويل احتيالي.

الدرس: هجمات overlay واعتراض SMS، متعلّمين منفصلين عادة، بيتجمعوا بشكل روتيني في قطعة malware حقيقية واحدة — الدفاعات محتاجة تفترض إن المهاجمين بيسلسلوا التقنيات كمان.

القاسم المشترك بين كل الحالات

  • الثقة هي الهدف: كل حالة أساءت استخدام حاجة المستخدم أو المطوّر أو النظام كان بيثق فيها افتراضيًا — أداة، SDK، منفذ شحن، رسالة نصية.
  • أضعف حلقة نادرًا ما تكون التطبيق الرئيسي: أدوات البناء وSDKs طرف تالت والـ firmware والبنية التحتية الفيزيائية سببوا ضرر بقد أي كود تطبيق بذاته.
  • الحجم بيفيد المهاجم: SDK أو أداة بناء واحدة مخترقة تقدر توصل بصمت لعشرات الملايين من الأجهزة مرة واحدة.
  • النظافة الأساسية لسه الأهم: أسرار hardcoded وتحقق ناقص ظهروا مرارًا، بفاصل سنين، عبر حوادث غير مرتبطة.
  • كل تقنية في الكورس ده بترتبط بحادثة حقيقية — دول مش مخاطر افتراضية، دول تاريخ موثّق.
