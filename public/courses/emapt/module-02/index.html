02عقلية الأمان مع الموبايل أولًا

ليه الموبايل مختلف

السببالمثال
اتصال دائمتطبيق مراسلة بيكمّل sync في الخلفية حتى على شبكة مطار غير موثوقة، عكس تطبيق Desktop اللي بيتصل بس وهو مفتوح
جهاز شخصيتطبيق بنك، إيميل الشغل، وصور العيلة على نفس الجهاز — اختراقه معناه اختراق التلاتة مع بعض
حدود الثقةالـ client شغّال على جهاز المستخدم (أو المهاجم) فمينفعش نثق فيه أبدًا
سطح هجوم أوسعالتطبيق، النظام، الشبكة، الـ backend، الـ SDKs، والهاردوير كلهم أهداف محتملة

التفكير كمختبر موبايل

  • الاستخدام مقابل الأمان: كل ضابط أمان بيضيف احتكاك، فالمطوّرين أحيانًا بيضعّفوا الحماية عشان يفضل التطبيق سلس.
  • دوافع الخصم: مكسب مالي، سرقة بيانات، احتيال، تجسس، وضرر سمعة.
  • أخطاء المطوّرين الشائعة: secrets hardcoded، تخزين غير آمن، الثقة في الـ client، غياب فحوصات server-side.
  • عقلية "التطبيق + البيئة": اختبر التطبيق مع الجهاز والشبكة والـ backend والأطراف التالتة مع بعض.

حالة دراسية: RewardsNow

تطبيق ولاء بيتجاهل إعادة الـ login لمدة 30 يوم (usability)، ورصيد النقاط بيتحسب جوه التطبيق مش على السيرفر (خطأ مطوّر). الدافع: استبدال نقاط وهمية بمنتجات حقيقية (احتيال مباشر). فهم الثغرة محتاج فحص الجهاز والتطبيق والشبكة والسيرفر مع بعض.

1. Root الجهاز → 2. تعديل التطبيق (تخطي فحص الرصيد) → 3. إعادة إرسال طلب نقاط وهمية → 4. السيرفر يقبله لغياب التحقق

حلقة ضعف واحدة — endpoint على السيرفر من غير تحقق — حوّلت ثغرة جوه التطبيق لخسارة مالية حقيقية.

نفس الثغرة بشكل مختلف: Broken Access Control على الويب غالبًا بتعديل parameter في الرابط، وعلى الموبايل زر مخفي في الواجهة بس الـ endpoint خلفه مش بيتحقق من حاجة. والـ Injection على الويب SQLi في فورم، وعلى الموبايل JavaScript بيتحقن عبر WebView bridge ويوصل لكود native — مسار مالهوش مثيل في الويب.

خصائص الموبايل الفريدة

  • الحساسات والهاردوير: كاميرا وGPS ومايكروفون وBluetooth وNFC ممكن تسرّب بيانات لو اتساء استخدامها (فلاشلايت بيطلب مايك من غير سبب وظيفي).
  • اتصال بين التطبيقات: Intents وdeep links وURL schemes ممكن تتستغل (deep link بيسجّل دخول صامت لحساب المهاجم).
  • الأمان المادي: جهاز مفقود أو مسروق بيكشف البيانات المحلية.
  • العمل Offline: البيانات الـ cached لازم تتحمي من غير سيرفر.
  • ثغرات خاصة بالمنصة: Android وiOS كل واحد له نقاط ضعفه (backdoor debug مش متاح إلا عبر ADB لسه خطر على جهاز مخترق).

03الـ Backend والـ Authentication

تدفق المصادقة

Sign In → Server يتحقق من creds + MFA → Access Token (قصير العمر) + Refresh Token (طويل العمر) → App يستخدم Access Token مع كل API call عبر TLS → لما ينتهي: Refresh Token يجيب Access Token جديد

الـ Access Token قصير العمر يقلّل الضرر لو اتسرق، والـ Refresh Token طويل العمر فلازم يتخزن بأمان ويكون قابل للإلغاء من السيرفر.

أنماط دفاع الـ API

  • TLS مفروض على كل الترافيك. مفيش Auth بالـ Cookies (التوكنز في الـ headers فـ CSRF التقليدي ملوش معنى هنا). App Attestation للتأكد إن الطلب جاي من تطبيق أصلي على جهاز موثوق. MFA يتحقق منه السيرفر مش التطبيق. إلغاء فوري للتوكنز المسروقة. فتح بالـ Biometric بيفك توكن مخزّن بدل ما يبعت بيانات خام.

تحليل الترافيك ونقاط الـ API الخاصة بالموبايل

  • Certificate pinning: التطبيق بيرفض شهادة الـ proxy بتاعتك. تطبيقات مش واعية بالـ proxy: بعض التطبيقات بتتجاهل إعدادات النظام. بروتوكولات مش HTTP: TCP مخصص أو MQTT أو WebSocket محتاجة أدوات تانية. Payloads موقّعة/مشفّرة: محمية فوق الـ TLS فمينفعش تعدّلها مباشرة.
  • Endpoints خاصة بالموبايل: تسجيل الجهاز (ربط جهاز/push token بحساب)، نسخ قديمة من الـ API لسه بتنادي endpoints أضعف، endpoints الـ attestation، وendpoints الـ sync اللي ممكن تكشف بيانات أكتر من الواجهة.

أمثلة من الواقع

  • تطبيق مشاركة ركوب: Refresh Token عمره 90 يوم من غير إلغاء — سرقة الموبايل معناها سرقة الحساب شهور.
  • تطبيق بنكي: MFA بيتفحص جوه الواجهة بس، فيتخطّى بنداء الـ login API مباشرة.
  • تطبيق توصيل أكل: API key hardcoded في الـ APK، اتلاقى بدقايق بالـ decompiler.
  • تطبيق لياقة: endpoint الـ sync بيتجاهل انتهاء صلاحية التوكن، فتوكن قديم مسروق لسه بيشتغل.
  • تطبيق تسوق: توكن الـ session في الـ query string، فبيتسجل في كل اللوجات.

اعتبارات قانونية وامتثال

  • CFAA: حدود الوصول المصرَّح بيه قانونيًا (أمريكا). DMCA: قانونية الـ reverse engineering. EULA: اتفاقيات ترخيص المستخدم ممكن تقيّد اللي تقدر تعمله وقت الاختبار.
  • الاختبار الدولي: الأطر القانونية بتختلف بين الدول. لوائح الاتصالات: اختبار وظائف شركات الاتصالات ليه جانب قانوني خاص. قوانين حماية البيانات: GDPR وCCPA وغيرها بتأثر على إزاي تتعامل مع البيانات أثناء الاختبار.

اختبر بس بتصريح مكتوب وجوه الحدود القانونية. تطبيق فلاشلايت "بريء" بيقرا بيانات clipboard من تطبيق بنكي، أو مقاول عنده صلاحيات admin بيصدّر أرقام تليفونات المستخدمين بهدوء — كلها سيناريوهات تهديد حقيقية لازم الـ threat model يغطيها.

سلسلة الإمداد بتشمل كل حاجة في تطوير وبناء وتوزيع وصيانة التطبيق: SDKs ومكتبات (analytics, ads, auth)، APIs موردين، أدوات بناء (Gradle, CocoaPods, npm)، وخدمات cloud/CI-CD.

متجهات هجوم سلسلة الإمداد

  • SDKs قديمة أو بها ثغرات. تسريب بيانات صامت (SDK بيبعت بيانات بهدوء). كود طرف تالت من غير sandbox. Binaries غير موثّقة وبدون SBOM.

08التحقق والتفويض (Authentication & Authorization)

المفاهيم الأساسية

  • Authentication: التحقق من هوية المستخدم. Authorization: تحديد صلاحيات وصوله. Session Management: الحفاظ على الجلسة وحمايتها. عوامل المصادقة: حاجة تعرفها، تملكها، أو تمثّلك. Trust Boundaries: نقاط بتتغير فيها متطلبات المصادقة.

تحديات الموبايل الخاصة

  • منطق على الـ client (فحوصات auth جوه الجهاز). قدرات Offline (تخزين اعتمادات أو توكنز). SDKs طرف تالت (OAuth/SSO ممكن ما تتحققش بالكامل). استمرار الجلسة طويل المدى. تخزين التوكن محليًا غالبًا بشكل غير آمن.

إدارة اعتمادات ضعيفة

  • سياسات باسورد ضعيفة. غياب حماية brute-force. مسارات استرجاع يمكن تخمينها. تخزين اعتمادات غير آمن. نقل اعتمادات نص عاري.

مصادقة Client-Side مكسورة

  • اعتمادات hardcoded. قرارات مصادقة على الجهاز. تطبيق biometric غير آمن. تخطّي فحوصات بالتلاعب بالـ client. MFA معيب يمكن تخطّيه.

إدارة Session غير آمنة

  • حماية توكن غير كافية. غياب انتهاء صلاحية. توليد توكن ضعيف. إبطال session غير صحيح وقت الخروج. مشاكل الـ session عبر أجهزة متعددة.

الطبقة الشبكية والمشاكل الشبكية

  • غياب أو سوء إعداد TLS. تخطّي التحقق من الشهادة. هجمات Downgrade. اتصال backend غير آمن.

كسر التفويض على مستوى الوظيفة

  • Horizontal Escalation (الوصول لبيانات مستخدمين تانيين). Vertical Escalation (الوصول لوظائف أعلى صلاحية). غياب فحص الصلاحية على بعض الـ endpoints. IDOR بمعرّفات متوقعة. Race Conditions تتخطى فحص الصلاحية.

عيوب التفويض من جهة الـ Client

  • منطق التفويض جوه الكود. عناصر واجهة مخفية بدل الحجب الحقيقي. التلاعب بفحوصات الجهاز. Deep links وIntent redirection. مكونات مكشوفة بحماية ضعيفة.

مخاطر الـ Content Provider وBroadcast Receiver

  • Providers متساهلة بتكشف بيانات أكتر من المطلوب. Receivers بتقبل broadcasts من أي تطبيق. هجمات عبر الـ Intents. مشاركة بيانات غير آمنة بين التطبيقات. غياب فحوصات الصلاحية.

نتائج حقيقية من الاختبار الديناميكي

  • تخطّي الـ Login عبر Frida أو تعديل الـ payload. تغيير userId ولسه بتتقبل البيانات. إنفاذ على الواجهة بس مش السيرفر. إعادة استخدام توكن طويل العمر عبر أجهزة متعددة. غياب تحقق من الـ access token في الطلبات المعترَضة. إعدادات OAuth خاطئة بتسرّب توكنز.

09التحقق من المدخلات والمخرجات

Input Validation: التأكد إن البيانات القادمة صحيحة وآمنة ومتوقعة قبل استخدامها. Output Validation: التأكد إن البيانات الخارجة من التطبيق متنقّاة عشان ما تستغلش الأنظمة اللي بتستقبلها (WebViews وAPIs وnative calls).

سطح هجوم المدخلات في الموبايل

  • حقول الواجهة. Deep links وURI schemes (myapp://login?token=...). ملفات خارجية ومحتوى يتم تحليله (PDF, XML, JSON). Intents وIPC. WebViews. بيانات الحساسات (GPS spoofing، microphone). Cloud sync (بيانات offline معدّلة بترجع للسيرفر). Clipboard. اللوجات ورسائل الخطأ.

ثغرات الحقن في الموبايل

  • SQL Injection على قواعد بيانات محلية. NoSQL Injection. XML Injection (بما فيها entity expansion). Command Injection في native code. JavaScript Injection جوه WebViews غالبًا توصل لجسر native.

XSS وتقنيات التخطّي

  • Stored / Reflected / DOM-based XSS جوه الـ WebView. استغلال الـ JavaScript Bridge. تخطّي الفحص: ترميز وأحرف خاصة، تلاعب في طول المدخل، تزوير نوع MIME، هجمات بنيوية على JSON/XML.

  • فشل ترميز HTML entities. ترميز JavaScript ناقص جوه WebViews. ترميز قيم SQL غير آمن. ترميز XML معيب. كشف تفاصيل في رسائل الخطأ. Logging حساس مفصّل.

تقنيات الاختبار

  • Mobile Fuzzing. اعتراض وتعديل الترافيك. كشف تخطّي التحقق وقت الـ runtime. Instrumentation لمراقبة فعلية لما بيتحقق منه الكود. أدوات fuzzing مخصصة للموبايل.

أمثلة: myapp://login?token=... بيسجّل دخول أي حد بيضغط على رابط مصمّم ومبعوت بـ SMS. PDF مرفوع غير منقّى بيعطّل التطبيق ويسرّب الذاكرة. رسالة chat غير منقّاة في WebView بتنفّذ JS ضد جسر التطبيق نفسه. شاشة خطأ بترجّع نفس اللي كتبه المهاجم. موقع GPS مزوّر بيفتح مكافأة "صالة قريبة" وهمية.

10الاتصال غير الآمن

أجهزة الموبايل بتعيش على شبكات معادية، فالترافيك محتاج نفس حماية التخزين المحلي.

الشهادة الرقمية والتحقق من TLS

الشهادة ملف من CA بيثبت هوية السيرفر، وبتحتوي على: المفتاح العام، اسم النطاق، معلومات المُصدِر، تاريخ الانتهاء، والتوقيع الرقمي.

Connect over HTTPS → Server presents certificate → App verifies issuer/domain/validity → Secure session established

أخطاء شائعة في التحقق من الشهادة

  • قبول كل الشهادات. السماح بشهادات self-signed. تعطيل hostname verification. استخدام شهادات منتهية أو ضعيفة. نسيان إعادة تفعيل التحقق بعد الـ debug.

Certificate Pinning

بيثق بس في شهادة أو مفتاح عام محدد، فحتى شهادة صحيحة من CA مزوّر (rogue CA MITM) بترفض. بيتنفّذ عبر شهادات/مفاتيح hardcoded، Android Network Security Config، أو iOS ATS + مكتبات SSL pinning.

iOS App Transport Security (ATS)

  • التطبيق الافتراضي: TLS 1.2+، forward secrecy، cipher suites قوية بس. NSAllowsArbitraryLoads: true أخطر override، بيلغي ATS تقريبًا بالكامل. NSExceptionDomains استثناءات لنطاقات معينة، دايمًا تستحق المراجعة. أول فحص static: افتح Info.plist وشوف المفتاح ده قبل أي اعتراض ترافيك.

علامات الاتصال غير الآمن

  • ترافيك ظاهر في Burp من غير مجهود (مفيش pinning). اعتمادات/توكنز عبر HTTP. نطاقات غير متوقعة (SDK طرف تالت بيسرّب). توكنز المصادقة في الـ query string. غياب أخطاء TLS مع شهادات غير صالحة. قيم نص عاري في اللوجات.

تقنيات الهجوم على ترافيك الموبايل

  • MITM (Burp, mitmproxy). TLS Downgrade. حقن شهادة مزيفة على جهاز rooted أو emulator. DNS Spoofing. تحليل البروتوكول (API وBLE). سرقة توكن/session.

أمثلة: تطبيق بنكي بيقبل أي شهادة لأن bypass الـ debug ما اتشالش. تطبيق تسوق بيظهر ترافيكه في Burp من غير أي مجهود (مفيش pinning خالص). تجديد شهادة روتيني بيكسر التطبيق لكل المستخدمين لحد ما يطلع تحديث طارئ (pinning متشدد جدًا). تطبيق سفر بيرجع لـ HTTP plaintext بدل ما يرفض الاتصال.

11الخصوصية في تطبيقات الموبايل

الخصوصية مش هي الأمان — تطبيق ممكن يكون آمن تقنيًا ولسه بينتهك خصوصية المستخدم.

القوانين المؤثرة

  • GDPR (الاتحاد الأوروبي). CCPA/CPRA (كاليفورنيا). PIPEDA (كندا). قواعد الخصوصية الخاصة بالـ App Stores (Apple وGoogle). لوائح قطاعية مثل HIPAA وGLBA. COPPA (خصوصية الأطفال).

فئات البيانات الشخصية الحساسة

  • معرّفات شخصية (اسم، إيميل). اعتمادات الحساب. بيانات مالية. بيانات بيومترية/صحية. معرّفات الجهاز (IMEI، advertising ID). بيانات الموقع. بيانات سلوكية.

أماكن تركّز مخاطر الخصوصية

  • جمع البيانات والـ minimization. التعريف والتتبع (fingerprinting وadvertising IDs). الاحتفاظ والحذف. المشاركة والتكامل مع طرف تالت. الموافقة والشفافية.

ثغرات خصوصية شائعة

  • استخدام صلاحيات زايد عن اللزوم. نقل بيانات غير آمن. معرّفات دائمة وfingerprinting. تجهيل بيانات غير كافٍ (خطر إعادة التعريف). تحليلات تنتهك الخصوصية (تسجيل الجلسة بالكامل). تسريب بيانات وصفية (EXIF في الصور).

منهجية اختبار الخصوصية

  • تحليل خصوصية ديناميكي (تتبع الترافيك وتدفق البيانات). تحليل سلوكي (مقارنة الممارسة الفعلية بالمُعلنة). خرائط وجرد البيانات. اختبار الموافقة والشفافية.

أمثلة: فلاشلايت بيطلب صلاحية موقع في الخلفية "لتحسين الإعلانات". تحليلات بتسجّل كل ضغطة بما فيها حقل "الأعراض" في تطبيق صحي. صور إجازة فيها EXIF location بتكشف عنوان البيت. معرّف جهاز فريد ملصق بكل حدث بيلغي أي "تجهيل" مزعوم.

12ضعف الحماية الثنائية (Insufficient Binary Protections)

أي حد يقدر يحمّل التطبيق ويعمله decompile ويحلله. الحماية الثنائية بتصعّب: فك التحليل، فهم المنطق الداخلي، تعديل فحوصات الأمان، حقن أو hook كود، واستخراج الأسرار.

ليه الـ Binaries معرّضة

  • سهلة الوصول (تحميل وdecompile). منطق الـ client ظاهر (أسرار ومنطق وتوكنز). العبث شائع (patching وrepackaging وتضمين malware). تهديد الـ repackaging (نسخ معدّلة توزّع malware). Runtime Hooking عبر Frida وXposed.

افتراضات خطيرة عن أمان الـ Binary

  • "Obfuscation = Security" — بس بيضيف احتكاك، مش بيشيل الثغرة. "APIs عندنا محمية" — حماية الـ API مستقلة عن حماية الـ binary. "محدش هيدوّر يعمل decompile" — أدوات الـ decompile مجانية وناضجة. "Anti-root = آمن" — فحص root وحده مش بيحمي الباقي.

إزاي المهاجم يستهدف الـ Binary

  • تعديل سلوك وقت التشغيل. Memory dumping. Method hooking/swizzling. اعتراض استدعاءات الدوال. حقن مكتبة native. إزالة obfuscation والـ instrumentation الديناميكي (Frida).

13الإعدادات غير الآمنة (Insecure Configuration)

الأسباب الشائعة

  • إعدادات افتراضية متسابة. ميزات خطيرة شغّالة في الإنتاج. قيم غير آمنة في config/manifest. صلاحيات زايد عن اللزوم. تشديد غير مكتمل.

ليه بتحصل كتير

  • التطبيقات بتيجي مع ملفات config كتير (مساحة أكبر لقيمة خاطئة). إعدادات الـ debug بتتنقل للإنتاج. Platform APIs قوية ومعقدة. SDKs طرف تالت بتجيب إعداداتها الخاصة. السلوك بيتغير بين بيئات dev/staging/production.

14التخزين غير الآمن (Insecure Data Storage)

الأجهزة شخصية ومادية وغالبًا بتتفقد أو تتسرق، والتطبيقات الـ offline محتاجة تخزين محلي، ومعظم المستخدمين ما بيشفّروش أجهزتهم، وأدوات الروت/الجيلبريك متاحة بسهولة، والتخزين المحلي بيأثر على التعرّض في الـ cloud كمان.

تخزين بيانات حساسة بنص عاري

  • اعتمادات نص عاري. تعرّض PII. بيانات دفع. بيانات صحية. توكنز مصادقة نص عاري. بيانات الموقع الجغرافي.

أماكن تخزين غير آمنة ومشاركة غير آمنة

  • ملفات/مجلدات قابلة للقراءة من أي حد. تخزين خارجي لبيانات حساسة. ملفات قاعدة بيانات غير محمية. ملفات مؤقتة محتواها حساس. نسخ احتياطية غير آمنة. أما المشاركة: سوء إعداد Content Provider، ثغرات مشاركة عبر Intent، تعرّض بيانات الـ Pasteboard، تسريب عبر URL scheme، تعرّض بيانات عبر التطبيقات.

مشاكل استمرارية البيانات

  • احتفاظ زايد بالبيانات. حذف غير مكتمل. استمرار البيانات بعد إزالة التثبيت. سوء إدارة الـ cache والنسخ الاحتياطية.

ليه التحقق القياسي من الشهادة مش كفاية

بيتحقق من سلسلة الثقة بس، مش هوية الشهادة المحددة. أي شهادة موقّعة من CA موثوق بتتقبل حتى لو من CA غير متوقع. متجر الثقة العادي فيه 150+ CA جذري موثوق ضمنيًا، وأي واحد منهم نقطة فشل واحدة. CA مخترق يقدر يصدر شهادات مزوّرة. الـ Pinning بيقيّد الثقة لشهادة أو مفتاح محدد بس.

تقنيات تخطّي Certificate Pinning

  • Dynamic Instrumentation (Frida, Objection). Xposed Modules (JustTrustMe, SSLUnpinning). تعديل الكود يدويًا (smali أو Java). إعادة تجميع التطبيق بإزالة منطق الـ pinning.

بيصعب التخطّي لما يكون فيه طبقات متعددة من الـ pinning: فحوصات متعددة مش واحد، على مستويات كود مختلفة (native وJava)، في وقت الإطلاق وكل طلب، مع كشف تلاعب وanti-hooking وفحص root/emulator مدمج مع الـ pinning.

إزاي Frida بيشتغل

Frida Server بيشتغل على الجهاز، وFrida Client بيشتغل على جهاز المختبر ويحقن JavaScript في العمليات المستهدفة. القدرات: Hooking للدوال والطرق، قراءة وتعديل الذاكرة، تتبّع التنفيذ، سرد الكلاسات والموديولات المحمّلة، استدعاء الدوال مباشرة، والتلاعب بكائنات Java/Kotlin/Objective-C وقت التشغيل.

أمثلة: حساب خصم ولاء وقت التشغيل بس — غير مرئي للمراجعة الـ static، اتلاقى بـ Frida في دقايق. إعادة تسمية binary الـ "su" بس كفاية لتخطّي فحص root من ملف واحد. Pinning على المفتاح العام فضل شغّال طول تجديد شهادة كامل من غير أي تحديث. WebView بتقبل JavaScript عشوائي بمجرد ما Frida يتخطّى فحص الـ integrity بتاعه.

17أساسيات الـ API

الـ API جسر بين التطبيق والخدمات الخلفية، وبيمكّن تبادل البيانات وتنفيذ الميزات والتفاعل عن بُعد. 83% من ترافيك تطبيقات الموبايل مدفوع بالـ APIs (Gartner, 2023).

ليه التطبيقات بتعتمد على الـ APIs

  • تفريغ المعالجة الثقيلة (auth والمنطق على الـ backend). تحديثات لحظية (مراسلة وإشعارات بتفضل حديثة). تطبيق أخف (منطق أقل على الجهاز = استجابة أسرع). قابلية التوسّع (إدارة بيانات مركزية).

أنواع الـ APIs

  • Backend APIs: RESTful (الأشيع)، GraphQL (بتكسب شعبية)، gRPC وWebSockets. Platform-Specific: iOS (UIKit, SwiftUI, Core Location, HealthKit) وAndroid (Google Play Services, Jetpack, Firebase). Third-Party: دفع (Stripe, PayPal)، سوشيال ميديا، خرائط، تحليلات.

عوامل خطر خاصة بالـ API في الموبايل

  • الـ endpoints وآليات الـ auth موجودة جوه كود التطبيق نفسه. خطر reverse engineering أعلى من الويب. التوكنز بتفضل صالحة لفترة أطول بكتير. ثغرات خاصة بالمنصة: Android (deep linking وintent-based attacks) وiOS (URL scheme manipulation ومشاكل shared keychain).

مشاكل أمان الـ API الشائعة

  • فحوصات تفويض غير كافية (BOLA/IDOR). كشف بيانات زايد (الرد بيرجّع أكتر من المطلوب للواجهة). مراجع كائن مباشرة غير آمنة (تغيير معرّف يكفي). تسريب وسوء إدارة التوكنز.

معمارية الـ API

Mobile App (presentation) → API Gateway (routing, auth, rate limiting, validation) → Backend Server (logic + storage) → response JSON

بنية JWT وثغراتها

Header.Payload.Signature
  • Algorithm Confusion / None — تخطّي التحقق من التوقيع بالكامل. مفاتيح توقيع ضعيفة — brute-force على HMAC secret. غياب التحقق من التوقيع. كشف معلومات في الـ payload. غياب التحقق من claims — قبول توكنز منتهية أو غير صالحة.

ممارسات JWT غير آمنة

  • مفاتيح تحقق hardcoded جوه الـ binary. تحقق من JWT على الـ client (الـ client نفسه مش موثوق). تخزين JWT في أماكن غير آمنة. انتهاء صلاحية طويل للاستخدام offline بيوسّع نافذة الخطر.

Session Fixation

1. المهاجم يجهّز Session ID معروف → 2. الضحية يُستدرج لاستخدامه → 3. الضحية يعمل login بنفس الـ session → 4. المهاجم يمتلك session مصادَق عليه بالكامل

طرق التوصيل: Deep links بـ parameter session (myapp://login?session=KNOWN_ID)، QR codes خبيثة، Cross-App Request Forgery، MITM، وروابط phishing عبر SMS/إيميل.

أمثلة: تغيير claim ID في الرابط بيكشف مطالبة طبية كاملة لمريض تاني. حقل "is_admin": true متقبول بيحوّل مستخدم عادي لـ admin فورًا. JWT موقّع بـ "none" يتقبل من السيرفر كتذكرة مزوّرة. Session ثابت في إيميل تسويقي — الضغط عليه بيسجّل دخول لحساب المهاجم أصلًا متحكم فيه.

21Brute Force وبصمة الجهاز والحماية من العبث

رسم تدفق الـ Login

راقب نداءات الـ API الفعلية، حدّد الـ parameters (username/email، password/OTP، session/token)، وحدّد بالظبط فين حماية الـ brute-force مفروضة — client-side ولا server-side.

أنماط تسجيل الدخول الشائعة في الموبايل

  • Username ← Password (التقليدي). Email/SMS OTP flows. Biometric مع fallback (PIN أو password احتياطي).

علامات حماية Brute-Force ضعيفة

  • محاولات login غير محدودة. غياب آلية lockout. غياب بصمة جهاز (مفيش إشارة إضافية لرصد محاولات مشبوهة). إعادة استخدام الـ session. غياب CAPTCHA.

بصمة الجهاز (Device Fingerprinting)

  • تحديد هوية الجهاز ومكان تسجيل الدخول. ربط الجهاز بالحساب/الـ session لمنع دخول غير مصرَّح أو هجمات replay. استخدامات شائعة: تطبيقات بنكية، توصيل OTP، تقييد استرجاع الباسورد. ممكن تكون دائمة (مربوطة بمستخدم) أو مؤقتة (مقتصرة على session واحدة).

تحديد هوية الجهاز على iOS

  • identifierForVendor بيتصفّر لو كل تطبيقات نفس المطوّر اتمسحت، إلا لو اتحفظ في الـ Keychain. DeviceCheck وApp Attest: attestation موثّق من Apple نفسها — أصعب بكتير يتزوّر من معرّف محلي. حتى على آيفون jailbroken، الـ vendor identifier بيفضل ثابت إلا لو اتعدّل عمدًا. المعنى للاختبار: محاكاة "أجهزة" متعددة على iOS محتاج تلاعب مقصود بالمعرّف، مش بس تشغيل emulators أكتر.

فحوصات البيئة والعبث اللي التطبيقات بتعملها

  • كشف Debugger مرتبط. كشف Emulator. كشف Frida/hooking frameworks. فحوصات Root/Jailbreak. كشف Magisk/Xposed.

اختبار بصمة الجهاز: Static وDynamic

  • Static: فين بيتقرا معرّف الجهاز (Settings.Secure.ANDROID_ID ومنطق تخزين UUID مخصص)، وأكواد كشف Emulator محددة (Build.FINGERPRINT أو ro.hardware).
  • Dynamic: Hook منطق البصمة بـ Frida، شغّل عدة emulators بمعرّفات مختلفة، حاكِ "أجهزة" منفصلة بالـ login، وراقب سلوك السيرفر (هل OTP اتمنع على الـ emulator التاني؟ هل التطبيق بيعمل logout أو error؟).

ليه التطبيقات بتحمي نفسها من العبث

  • حماية بيانات وتخزين حساس (Keychain/Keystore). منع تعديل الكود (instrumentation أو binary patching). حماية DRM وanti-cheat والملكية الفكرية. منع تخطّي منطق العمل (شراء مجاني أو تخطّي ترخيص). الامتثال لمتطلبات (مثل PCI DSS للتطبيقات البنكية).

أمثلة: محاولات OTP غير محدودة بتخلي brute-force الكود مسألة دقايق. Emulatorين بمعرّفين مختلفين بيسجلوا دخول في نفس الوقت من غير إنذار. فحص Frida بيحصل عند الإطلاق بس، فحقن الأداة بعد ثواني من البدء بيتخطّاه بالكامل.

24Static Analysis وسطح الهجوم وThreat Modeling

فك تجميع التطبيق

  • التقاط وتحليل أولي للترافيك. جرد endpoints من الملاحظة الفعلية. توثيق تدفق المصادقة فعليًا عبر السلك. أنماط نقل البيانات (كمية، تكرار، طريقة). كشف Certificate Pinning ومدى تشدده.

  • بصمة تقنية السيرفر. تحديد خدمات الـ cloud. اكتشاف تكاملات API طرف تالت. تحديد سيرفر المصادقة فعليًا. كشف أنظمة قواعد البيانات والتخزين.

  • Data Flow Diagrams (تصوّر حركة البيانات). Trust Boundaries (نقاط تغيّر افتراضات الثقة). تحديد تهديدات بـ STRIDE. ترتيب أولوية الخطر للاختبار. تطوير Attack Trees للسيناريوهات متعددة الخطوات.

  • تحديد وتقييم قيمة الأصول. تطوير سيناريوهات تهديد واقعية. تقدير احتمالية الثغرة. تقييم التأثير لو كل متجه نجح. ترتيب وتصنيف الخطر لتحديد ترتيب الاختبار.

  • الوظائف عالية الخطورة أولًا. التركيز على المصادقة والتفويض (عادة أعلى قيمة). أولوية معالجة البيانات الحساسة. اهتمامات العميل المحددة. توازن بين الشمول والعمق.

أمثلة: endpoint واحد يوصله من الشبكة والـ client والـ backend في نفس الوقت — أولوية فورية. STRIDE بيكشف مسار انتحال هوية كان غير مرئي في مراجعة سطحية. سيناريو متسلسل (IDOR + تخزين غير آمن) بيثبت خسارة مالية فعلية.

أربع نقاط تفتيش — واحدة بعد كل مرحلة ما عدا الأخيرة — بتحافظ على الاشتباك في مساره.

المرحلة 1: الانطلاق والتجهيز

  • اجتماع Kickoff: تعريف الفريق، مراجعة النطاق والأهداف، تأكيد الجدول والمخرجات، توفير وصول أولي.
  • Recon أولي: تثبيت وضبط التطبيق، استخدام أولي ورسم خريطة، التقاط ترافيك مبدئي، تحقق من الأدوات والـ static analysis.

Checkpoint 1: التحقق من النطاق وتحسين الخطة

تأكيد جاهزية البيئة، التحقق من إصدار وبناء التطبيق الصحيح، ضمان وصول الأنظمة المطلوبة، تحديد تعديلات النطاق مبكرًا، وتحسين خطة الاختبار بناءً على نتائج الـ Recon الفعلية.

المرحلة 2: الاختبار الأساسي

  • المصادقة والتفويض: تحليل آلية المصادقة، اختبار إدارة الـ session، التحقق من ضوابط التفويض، اختبار الوصول حسب الدور، تقييم MFA.
  • التخزين والحماية: أمان التخزين المحلي، التحقق من تنفيذ التشفير، التحقق من التعامل مع البيانات الحساسة، اختبار أمان النسخ الاحتياطي، اختبار تسريب البيانات.
  • اتصال الشبكة: التحقق من أمان النقل، اختبار أمان كل endpoint على حدة، التحقق من تنفيذ SSL/TLS، تقييم Certificate Pinning، أمان الاتصال مع الـ backend بالكامل.

Checkpoint 2: مراجعة النتائج الحرجة

توثيق فوري للنتائج الحرجة (ما بتستناش التقرير النهائي)، تحقق أولي من الخطورة، إخطار العميل فورًا بالقضايا الكبيرة، تعديل تركيز الاختبار، وتقييم التقدم بصدق مقابل الخطة الأصلية.

المرحلة 3: اختبار متقدّم واستغلال

  • تفاعل المنصة: اختبار IPC، فحص معالجات URL scheme المخصصة، تقييم أمان الـ Clipboard، اختبار ثغرات Intent/Deep Link، أمان تنفيذ WebView.
  • منطق العمل: محاولات تخطّي سير العمل، التحقق من قواعد العمل، اختبار أمان المعاملات (حيث تتحرك الأموال أو القيمة)، اختبار Race Conditions، صيد العيوب المنطقية الدقيقة.
  • الحقن من جهة الـ Client: حقن عبر WebView، حقن التخزين المحلي، التلاعب بـ parsers XML/JSON، حقن عبر بروتوكولات مخصصة، محاولات تخطّي التحقق من المدخلات.

Checkpoint 3: تقدّم الاستغلال

توثيق الاستغلال الناجح فور حدوثه، تقييم تسلسل الهجمات، جمع أدلة استغلال قوية (مش مجرد ادعاءات)، تجهيز لإظهار التأثير، والتحقق من تغطية الاختبار.

المرحلة 5: إعداد التقرير

  • التحقق من النتائج: إعادة إثبات الثغرة، إزالة False Positives، تحديد تصنيف الخطر، تصنيف النتائج، تحسين إثبات الاستغلال.
  • التقرير الفني: توثيق تفصيلي للثغرات، وضوح خطوات إعادة الإنتاج، إدراج أدلة فنية، تحليل السبب الجذري، توصيات معالجة مفصّلة.
  • الملخص التنفيذي: تقييم الخطر الكلي، أبرز النتائج، خريطة طريق استراتيجية للمعالجة، وضع أمني مقارن، شرح التأثير على العمل.

Checkpoint الأخير: تسليم ومراجعة التقرير

عرض التقرير مباشرة للفريق التقني، شرح وتوضيح النتائج، مناقشة استراتيجية المعالجة، تخطيط وجدولة إعادة الاختبار (retest) للتأكد من فعالية الإصلاح، وإغلاق الاشتباك بصورة منظمة مع جمع الـ feedback.

أمثلة: تغيّر إصدار التطبيق اتلاقى مبكرًا عند Checkpoint 1 مش وقت التقرير. ثغرة حرجة في تحويل الأموال وصلت للعميل خلال أيام في Checkpoint 2 مش أسابيع. ملخص تنفيذي بيربط ثغرة تخزين بتأثير امتثال حقيقي يفهمه صاحب القرار.
