01ليه أمن الموبايل مهم (Why Mobile Security Matters)

أرقام بتوضّح الحجم

الرقمالمعنى الأمني
+8.5 مليار مستخدمجمهور ضخم ومتصل طول الوقت، فأي ثغرة تأثيرها كبير
~4 ساعات يوميًامتوسط وقت الاستخدام لكل شخص
88% داخل التطبيقاتمعظم الوقت جوه apps مش المتصفح، فالتطبيق هو السطح الأساسي للهجوم
Platform Dependentتطبيق Android وتطبيق iOS عمليًا codebase منفصلين (Kotlin/Java مقابل Swift)، فلازم يتأمّنوا ويتختبروا مرتين

إيه معنى "Platform Dependent" بالظبط؟

التطبيق الـ native بيتكتب مرتين: نسخة Android (Kotlin/Java) ونسخة iOS (Swift/Obj-C)، ولكل نسخة لغة وframework ونموذج أمان مختلف. يعني تطبيق بنك لازم يتأمّن ويتختبر مرتين، وثغرة في واحدة مش شرط تكون في التانية. وعشان المستخدم قاعد في التطبيق ~3.5 ساعة يوميًا، ثغرة واحدة في تطبيق مراسلة مشهور ممكن تأثر على مئات الملايين من الـ sessions قبل ما حد يكتشفها. ده السبب إن الموبايل بقى هدف أساسي مش حاجة ثانوية في برامج الأمان.

مشاكل الأمان الشائعة في الموبايل

التحديشكله في تطبيق حقيقي

OS Vulnerabilitiesنظام قديم ناقصه patch لثغرة kernel أو WebView

أصحاب المصلحة والاتجاهات المستقبلية

  • Developers: يكتبوا كود آمن. Organizations: تملك الخطر وتوازن بين الميزات والتكلفة والأمان. Users: يثقوا في التطبيق. Security Professionals: يختبروا ويقلّلوا الخطر.
  • IoT: التطبيق اللي بيفتح قفل ذكي لازم يحمي نفسه والجهاز.
  • AI: بتحسّن الـ phishing عند المهاجم، وبتسرّع اكتشاف السلوك الشاذ عند المدافع.
  • Regulations: زي GDPR بتفرض تبرير كل بيان شخصي بيتجمع.
  • BYOD & Zero Trust: موبايل الموظف الشخصي بيتعامل كغير موثوق لحد ما يثبت هويته في كل طلب.

الـ Static مش هيكشف ثغرات الـ runtime، والـ Dynamic ممكن يكشف سلوك مش ظاهر في الكود. عادةً بنعمل الاتنين.

ليه بنختبر وتفاصيل الـ Static والـ Dynamic

  • الـ Static: بتفحص الـ APK/IPA أو الكود من غير تشغيل. بيدّيك فكرة عامة عن التطبيق وبيكشف secrets وendpoints وإعدادات ضعيفة، بس مش هيكشف ثغرات الـ runtime، وممكن يكون مرهق لو مش مطوّر لأنك بتقرا كود decompiled.
  • الـ Dynamic: بتشغّل التطبيق وتراقبه. بيكشف مثلًا credentials بتتبعت من غير تشفير، أو credentials متخزنة على الجهاز، وعيوب business logic (مثلًا حقل amount العميل بيثق فيه والسيرفر مش بيتحقق منه).
  • ليه نختبر؟ التوقعات بتختلف: الـ Bug Bounty hunter بيدوّر على ثغرة قابلة للإثبات، والـ pentester بيغطي scope كامل، والـ consultant بيقدّم تقرير للعميل بتوصيات.
  • طرق الاختبار: Penetration testing، Vulnerability analysis، Threat modeling، Source code analysis.

مراحل الـ Pentest الخمسة

1. Pre-engagement → 2. Recon → 3. App Mapping → 4. Exploitation → 5. Reporting
  • Pre-engagement: الـ scope، توقعات العميل واللوائح، وممكن تحتاج نسخة اختبار. حدّد البيانات الحساسة (Authentication data, PII, بيانات محمية قانونًا)، وفين بتتخزن وبتتبعت وإزاي.
  • عناصر أمنية تدوّر عليها: Hashing, Encryption, Encoding, Token storage, Random number generators.
  • Recon: غرض التطبيق، مطوّره، الصناعة، وإزاي بيشتغل.
  • App Mapping: المعمارية، إدارة الـ sessions، الاتصالات، وThreat Modeling.
  • Exploitation: مش كل ثغرة قابلة للاستغلال، قيّم: Damage، Discoverability، Reproducibility، Exploitability، وعدد المتأثرين.
  • Reporting: Executive summary، Scope، Methods، Findings، Recommendations.

مثال بنك: الـ scope = تطبيق Android والـ API بس ← Recon على الـ API docs ← اعتراض الترافيك يوريك token وendpoint /transfer ← تكتشف إنه مش بيتحقق إن الـ token بتاع صاحب الحساب المخصوم منه ← توثّق التأثير وخطوات التكرار وتوصي بفحص ملكية server-side.

05منصة Android وأمانها

Android مبني على Linux kernel ومفتوح المصدر، أرخص وأوسع انتشارًا وأسهل في الاختبار من المنصات المغلقة.

طبقات المعمارية (من تحت لفوق)

الطبقةالدور
Android Kernelقلب النظام ويكلّم الهاردوير (مش مهم لاختبار التطبيقات)
Native Daemons & Librariesعمليات خلفية بتتعامل مع الـ kernel مباشرة
HALبيخلّي موردي الهاردوير ينفّذوا ميزات من غير تعديل الطبقات الأعلى
ARTبيترجم bytecode للتطبيق لتعليمات خاصة بالمعالج
System Services"قلب Android": power, clipboard, notification, alarm managers...
Android Framework / APIكلاسات Java اللي التطبيقات مبنية عليها، والـ API العام جزء منها
System APIللشركاء وOEMs بس (Device Manufacturer Apps / privileged)
Android Appاللي بنختبره غالبًا

أربع نطاقات للأمان (Defense in Depth)

النطاقالمحتوى
System-Wideتشفير الجهاز (FDE من Android 5، وFBE بمفاتيح مختلفة مع Direct Boot)، TEE لتوليد المفاتيح، Verified Boot
Software IsolationSandbox، users، SELinux، permissions
NetworkTLS افتراضيًا، DNS over TLS، والـ cleartext محجوب افتراضيًا من Android 9
Anti-ExploitationASLR, KASLR, PIE, DEP, SECCOMP

Verified Boot Chain: Boot ROM → Bootloader → Boot Partition → System Partition، كل مرحلة بتتحقق من اللي بعدها.

Sandbox وSELinux وحالات العملية

  • كل تطبيق بيشتغل كـ Linux user مختلف، وبياناته معزولة. المشاركة ممكنة لو الشهادة نفسها أو sharedUserId في الـ manifest.
  • Zygote: عملية بتبدأ وقت الـ boot وبتحمّل الكلاسات والمكتبات وART، وكل تطبيق جديد بيتعمله fork منها (copy-on-write) فالتشغيل أسرع وبياخد ذاكرة أقل.
  • حالات العملية: Foreground، Visible، Service، Cached (أول واحدة تتقتل). للمختبر: الـ Service ممكن يفضل شغّال في الخلفية، فافحص هو بيعمل إيه.
  • SELinux: Mandatory Access Control حتى على root. Enforcing بيمنع ويسجّل (الافتراضي)، وPermissive بيسجّل بس (شائع على أجهزة الاختبار).

إزاي التطبيق بيشتغل (How Does an App Run?)

User taps icon → Activity Manager checks if running → Zygote forks process → AMS coordinates launch → OS manages memory
  • الـ Activity Manager (جزء من System Server) بيستقبل الطلب ويشوف هل التطبيق شغّال. لو شغّال بيرجّعه للـ foreground، ولو لا بيتعمل process جديد من Zygote.
  • لو الذاكرة قليلة النظام ممكن يقتل عمليات الخلفية، ولو المستخدم قفل التطبيق العملية ممكن تفضل في الذاكرة عشان إعادة فتح أسرع.
  • Zygote وقت الـ boot: بيحمّل كلاسات الـ framework (android.app.*, android.os.*, android.view.*) ومكتبات (graphics, networking, media) ويجهّز ART/Dalvik. الـ child process بيورّث كل ده فالمشاركة بتوفر ذاكرة ووقت.

الـ Exported Components: المخاطر والتخفيف

لما المكوّن يبقى android:exported="true" أي تطبيق على الجهاز (حتى الخبيث) يقدر يستدعيه ويسرق بيانات أو يغيّر السلوك أو يرفع صلاحياته.

المكوّنالخطرالتخفيف
Exported ActivityUI hijacking وintent injectionexported="false" إلا لو ضروري
Exported Serviceتنفيذ أوامر من تطبيق تاني (ممكن توصل لـ RCE)تقييده بـ permission
Exported ReceiverIntent hijacking وbroadcasts مزوّرةexplicit broadcasts أو exported="false"
Exported Providerتسريب بيانات (path traversal أو query غير منقّاة)exported="false" أو permissions

مثال عملي في الاختبار: بتستدعي Activity مكشوفة مباشرة (بـ adb أو Drozer) وتشوف هل بتفتح شاشة داخلية من غير ما تعدّي على الـ login.

07منصة iOS وتحليل Info.plist

معمارية أمان iOS

iOS بيئة أكتر تقييدًا: التطبيقات معزولة، وصول الـ System API محدود، وعدد قليل من آليات الـ IPC.

الموضوعالتفاصيل
Secure Boot ChainBoot ROM (read-only) ← Low-Level Bootloader ← iOS Kernel، ولو أي signature فشل الـ boot بيقف
Code Signingكود معتمد من Apple بس هو اللي بيشتغل

Sandboxبيتفرض على مستوى الـ kernel، كل التطبيقات تحت نفس الـ user، وكل تطبيق محصور في مجلده

DeviceCheck / App Attestتحقق هاردوير من سلامة التطبيق ومنع cheats

جهاز Jailbroken بيشيل حدود الـ sandbox. تأكد إن النتيجة مش معتمدة على jailbreak قبل ما تبلّغ إنها قابلة للاستغلال على جهاز عادي.

10Threat Modeling

إيه هو الـ Threat Modeling؟

عملية منظّمة لتحديد وتحليل وتخفيف المخاطر بدري. الأسئلة الأربعة: What are we building? What can go wrong? What are we doing about it? Did we do a good job?

Understand the System → Identify Threats → Analyze Risks → Implement Countermeasures

أفضل وقت ليه مرحلة التصميم، وبيتراجع كل ما المعمارية تتغير أو ميزة كبيرة تتضاف أو integration جديد.

فهم النظام

  • Components: التطبيق، السيرفر، الـ APIs، الـ SDKs. Data flow: مسار بيانات المستخدم. Entry points: login، APIs، رفع الملفات.
  • Trust Boundary: خط تتغير عنده درجة الثقة، وهناك بتظهر مخاطر السرية والسلامة.
الحدّالخطرالتخفيف
User ↔ Appتلاعب بالمدخلات، reverse engineering، نسخ معدّلةInput validation، obfuscation، anti-RE
App ↔ Backend APIMITM، سرقة token، إساءة استخدام APITLS، tokens، rate limiting
App ↔ Local StorageMalware، أجهزة rootedتخزين مشفّر، Keystore/Keychain
Backend ↔ Third-partyتسريب API keysToken expiration، IP whitelisting، zero trust
User ↔ AdminPrivilege escalationRBAC وLeast privilege

الأصول وسطح الهجوم

  • الأصول (Assets): بيانات المستخدم، API keys، بيانات الدفع، authentication tokens.
  • Threat actors شائعين: مهاجم خارجي، insider خبيث، جهاز مخترق (compromised device).
  • Entry points وAttack vectors: User inputs (فورمز وحقول auth)، API endpoints ونقل البيانات، Device storage (logs وshared preferences)، External libraries.
  • مخاطر شائعة: Broken Authentication (session hijacking وتخزين token غير آمن)، Insecure Storage، Insecure Communication، RE & Code Tampering، Supply Chain (SDK خبيث).

حالات دراسية

  • Uber (2016): API keys مكتوبة جوه التطبيق اتسحبت واتستخدمت للوصول غير المصرَّح. الحل: معالجة آمنة للمفاتيح وتقييدها بالسيرفر.
  • WhatsApp GIF (2019): ملف GIF معدّ خصيصًا نفّذ كود عبر memory corruption في Android. الحل: إدارة ذاكرة آمنة وتنقية مدخلات صارمة.

DREAD (تحليل المخاطر)

Damage، Reproducibility، Exploitability، Affected Users، Discoverability، وكل عامل بدرجة 1 لـ 10.

أمثلة كود Android تنفع تفتكر شكلها

// Insecure Logging: بيسرّب credentials للـ logs
LOGGER.info("Login - Username: " + username + ", Password: " + password);

// WebView: URL جاي من intent من غير تحقق
String url = getIntent().getStringExtra("url");
webView.loadUrl(url);
webView.getSettings().setJavaScriptEnabled(true);

// Insecure SSL: TrustManager بيقبل أي شهادة
override fun checkServerTrusted(chain: Array<X509Certificate>, t: String) {}

// Reflection: استدعاء method خاصة
method.setAccessible(true);
method.invoke(cls.newInstance());

إزاي تلاقيهم: في الـ WebView دوّر على setJavaScriptEnabled(true) وloadUrl() اللي بتاخد مدخلات خارجية. وفي الشبكة دوّر على روابط HTTP وأي custom SSL handling بيتجاهل الـ verification. وفي الـ crypto دوّر على مفاتيح hardcoded وMD5/SHA-1 وECB. وكل ده بيخالف GDPR وPCI-DSS وHIPAA وISO 27001 لو فيه بيانات حساسة.

14كتابة التقرير (Reporting)

الاختبار بتاعك قيمته من قيمة تقريرك. استخدم لغة مهنية ومحايدة، متلومش المطوّرين، وخلّي التوصيات واقعية وقابلة للتنفيذ.

القسمالمحتوى

شكل الـ Finding الجيد

  • Title & Reference: "Insecure Data Storage، OWASP M9" وليس "تخزين سيئ"، مع CWE.
  • Evidence: لقطة أو log بيوري الـ credential نفسه.
  • Business Impact: "مهاجم عنده وصول فعلي للجهاز يقدر يستولي على أي حساب".
  • Reproduction Steps: خطوات مرقّمة يقدر المطوّر يكرّرها.
