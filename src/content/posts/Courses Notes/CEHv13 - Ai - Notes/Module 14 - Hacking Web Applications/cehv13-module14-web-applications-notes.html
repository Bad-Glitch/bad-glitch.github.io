01مفاهيم الـ Web Applications وWeb Services

كيف تعمل الـ Web Applications؟

الـ Web Application توفّر واجهة بين المستخدمين ونهائيين والـ Web Servers عبر صفحات ويب يُولَّد بعضها من السيرفر أو تحتوي كودًا ينفَّذ ديناميكيًا داخل متصفح العميل. وظيفتها الأساسية جلب البيانات المطلوبة من قاعدة البيانات وعرضها.

الطبقةالوصف
Client / Presentation Layerالطبقة التي يتعامل معها المستخدم مباشرةً (المتصفح والواجهة)
Business Logic Layerتحتوي قواعد العمل والمعالجة — مكتوبة بلغات مثل .NET وJava
Database Layerتُخزِّن البيانات الحسّاسة (IDs وكلمات المرور وبيانات العملاء)

بنية الـ Web Service

الـ Web Service تطبيق مُنشَر على الإنترنت يستخدم بروتوكول رسائل قياسي (مثل SOAP) لتمكين التواصل بين تطبيقات مبنية على منصّات مختلفة. تتفاعل عبر SOAP وUDDI وWSDL وREST.

الدور / المكوّنالشرح

Service Requesterالتطبيق أو العميل الباحث عن خدمة — المتصفح عادةً
Service Registryالمكان الذي يُحمِّل فيه المزوّد توصيف الخدمة — يُستخدَم للاكتشاف والربط
Serviceوحدة برمجية يُقدِّمها المزوّد — تتواصل مع الطالبين وقد تستدعي خدمات أخرى
Service Descriptionتوصيف الواجهة والتنفيذ — يحتوي كل العمليات والمواقع والبيانات والأنواع
UDDIUniversal Description, Discovery, and Integration — دليل يُدرِج الخدمات المتاحة
WSDLWeb Services Description Language — XML لوصف وتتبّع Web Services
WS-Securityامتداد لـ SOAP يحافظ على سلامة وسرية رسائل SOAP ويُصادِق المستخدمين
النوعالفلسفة

RESTfulأسلوب معماري يستخدم مفاهيم HTTP — أكثر مرونةً وأقل تعقيدًا من SOAP

Web-based Timing Attacks

النوعالشرح
Direct Timing Attackقياس الوقت التقريبي لمعالجة السيرفر لطلب POST لاستنتاج وجود اسم مستخدم
Cross-site Timing Attackإرسال حزم طلب مصمَّمة للموقع عبر JavaScript لقياس وقت الاستجابة
Browser-based Timing Attackاستغلال التسرّبات الجانبية في المتصفح لتقدير وقت معالجة الموارد — مثل Cache Storage Timing Attack لقياس حجم الاستجابة من وقت تحميل القرص

XML External Entity (XXE) Attack

هجوم SSRF يحدث لما محلّل XML بإعدادات خاطئة يسمح بمعالجة إدخال XML من مصدر غير موثوق. المهاجم يُضمِّن إشارةً لكيان خارجي في الإدخال الخبيث، فبعد معالجته يقدر يصل لملفات وخدمات محميّة من السيرفرات أو الشبكات المتصلة.

Unvalidated Redirects and Forwards

النوعالأثر
Unsafe Redirectsتنصيب Malware أو خداع الضحايا للكشف عن كلمات مرور ومعلومات حسّاسة
Unsafe Forwardsتجاوز Access Control → Session Fixation أو Security Management Exploits أو Failure to Restrict URL Access
نوع الـ Redirectionالشرح
Open Redirectionثغرة تسمح بإضافة Parameters للـ URL لتحويل المستخدمين من مواقع موثوقة لمواقع خبيثة — Credential Sniffing وXSS
Header-Based Open Redirectionتعديل HTTP Location Header لتحويل المستخدم لصفحة خبيثة بدون علمه
JavaScript-Based Open Redirectionحقن JavaScript في استجابة صفحة ويب — يُستخدَم كثيرًا في التصيّد

Magecart Attack وWatering Hole Attack

الهجومالآلية
Magecart (Web Skimming)حقن كود خبيث في موقع تجارة إلكتروني لجمع بيانات بطاقات الائتمان — يستهدف مواقع بإضافات أو برمجيات قديمة
Watering Hole Attackتحديد المواقع التي يزورها الهدف ← اختبار ثغراتها ← حقن كود خبيث يُعيد توجيه الصفحة أو يُحمِّل Malware. يُسمّى "Watering Hole" لأن المهاجم ينتظر الضحية تقع في الفخ

CSRF وCookie/Session Poisoning

الهجومالآلية
CSRF (One-Click / Session Riding)استغلال ثغرات صفحة ويب لإجبار متصفح المستخدم على إرسال طلبات خبيثة — الضحية عنده جلسة نشطة مع موقع موثوق ويزور موقعًا خبيثًا يحقن HTTP Request للموقع الموثوق في جلسته
Cookie Poisoningتعديل محتوى الـ Cookie على جهة العميل قبل إرسال الطلب للسيرفر — يسمح بالتلاعب بالـ Session State وUser ID وبيانات هوية أخرى. Cookie تُعدَّل بـ JavaScript أو Proxy

Insecure Deserialization

الـ Serialization يحوّل كائنات البيانات لتنسيق خطي للنقل. المهاجم يحقن كودًا خبيثًا في البيانات المُسلسَلة ويُرسِلها للضحية. عند إلغاء التسلسل (Deserialization) يُنفَّذ الكود الخبيث المحقون ويخترق النظام أو الشبكة.

Web Service Attacks

الهجومالشرح
Web Service Footprintingاستخدام Universal Business Registry (UBR) — سجل عام يعمل بـ UDDI وSOAP — لجمع معلومات عن الـ Web Services (مشابه لـ Whois)
XML Poisoningحقن كود XML خبيث في طلبات SOAP لتلاعب في عقد XML أو تسميم مخطّط XML — يُولِّد أخطاء في منطق تحليل XML ويُعطِّل منطق التنفيذ. يؤدّي لـ DoS أو كشف معلومات سرية
SOAPAction Spoofingالتلاعب في عملية SOAPAction Header دون الحاجة لـ XML Parsing — أداة WS-Attacker
WS-Address Spoofingإرسال رسالة SOAP تحتوي بيانات WS-Address مزوَّرة — Header ReplyTo يحتوي عنوان المهاجم بدل عنوان العميل
XML Poisoning مقابل SQL Injection

XML Poisoning مشابه لـ SQL Injection لكن بمعدّل نجاح أعلى في بيئة Web Service. المهاجم يسمِّم حركة البيانات بين السيرفر والمتصفح بإنشاء مستندات XML خبيثة تُغيِّر آليات التحليل مثل SAX وDOM.

DNS Rebinding Attack

تجاوز قيود Same-Origin Policy بتقنية DNS Rebinding — المهاجم ينشئ موقعًا خبيثًا ويسجّل دومينه مع سيرفر DNS يتحكّم فيه، ويضبط استجابات DNS بقيم TTL قصيرة جدًا لتجنّب الـ Caching. هذا يُتيح للموقع الخبيث التواصل وإرسال طلبات عشوائية للدومينات المحلية.

Clickjacking Attack

المهاجم يخدع الضحية للنقر على عنصر ويب خبيث مُوضَع بشكل شفّاف فوق صفحة موثوقة. هو مجموعة متنوّعة من تقنيات UI Redress Attacks — يستغل ثغرات HTML iframes أو الإعداد الخاطئ لـ X-Frame-Options Header.

MarioNet Attack

هجوم مبني على المتصفح يُشغِّل كودًا خبيثًا داخله — العدوى تستمرّ حتى بعد إغلاق صفحة الاختراق أو التصفّح بعيدًا عنها. المهاجم يُسجِّل ويُفعِّل Service Worker API عبر موقع يتحكّم فيه. عند تصفّح الضحية للموقع، يتفعّل Service Worker تلقائيًا ويشتغل بصمت في الخلفية. يُستخدَم لإنشاء Botnet وشنّ هجمات مثل Cryptojacking وDDoS وClick Fraud وكسر كلمات المرور الموزَّع.

هجمات أخرى

الهجومالشرح
Cookie Snoopingتحليل عادات تصفّح الضحية وبيع المعلومات لمهاجمين آخرين أو استخدامها لشنّ هجمات
RC4 NOMORE Attackهجوم على RC4 Stream Cipher يستغل ثغرات في السيرفر لفكّ تشفير Web Cookies المحميّة بـ HTTPS وحقن حزم عشوائية
Buffer Overflowالفشل في حماية الـ Buffer والسماح بالكتابة خارج حجمه الأقصى
CAPTCHA Attacksاستهداف الاختبارات التحقّقية لتجاوزها رغم تصميمها كمقاومة للآلات
DoSتقليل أو تقييد أو منع وصول المستخدمين الشرعيين لموارد النظام
DMZ Protocol Attacksاختراق نظام يسمح بالوصول لبروتوكولات DMZ أخرى يُعطي وصولًا للأنظمة الداخلية

Attack Hidden Form Fields

تطبيقات e-Commerce تستخدم Hidden HTML Form Fields لتخزين الأسعار. المهاجم يحفظ الـ Source Code، يحدّد الحقل المخفي، يعدّل قيمة السعر (حتى قيم سالبة لاسترداد المبلغ)، ثم يُعيد التحميل. يُستخدَم Burp Suite لاعتراض الطلب وتعديله.

هجوم Password Reset Poisoning

1
جمع معلومات الهدف

المهاجم يحصل على عنوان البريد الإلكتروني للهدف بالـ OSINT والهندسة الاجتماعية.

2
تعديل Host Header

إرسال طلب إعادة تعيين كلمة المرور بـ Host Header معدَّل — السيرفر يُنشئ رابط إعادة التعيين بناءً على الـ Host Header. مثال: Host: badhost.com فيُنشَأ رابط https://badhost.com/reset-password.php?token=87654321

3
انتظار الضحية

المهاجم ينتظر الضحية تضغط الرابط الخبيث في البريد.

4
سرقة الـ Token

بعد الضغط على الرابط، المهاجم يستخرج Password Reset Token وينفّذ أنشطة خبيثة.

5 — Attack Authorization Schemes

  • الدخول بحساب صلاحيات منخفضة ثم تصعيد الصلاحيات للوصول للموارد المحميّة
  • التلاعب في طلبات HTTP بتعديل حقول الإدخال المتعلّقة بـ User ID وUsername وAccess Group وCost وFilenames
  • Cookie Parameter Tampering: جمع Session Cookies وتحليل آلية توليدها ثم التلاعب بباراميتراتها بـ Burp Suite وإعادة تشغيل التطبيق

8 — Perform Injection/Input Validation Attacks

نوع الـ Injectionالشرح

OS Command Injectionحقن كود خبيث في حقول الإدخال عندما التطبيق يستخدم المدخل في أمر على مستوى النظام

9 — Attack Application Logic Flaws

معظم ثغرات المنطق بسبب إهمال المطوّرين أو افتراضات خاطئة. مثال: في تطبيقات التجزئة، المطوّر يفترض أن العميل سيتبع مراحل الطلب بالتسلسل (اختيار المنتج ← تأكيد الطلب ← الدفع ← التسليم). المهاجم يستخدم Burp Suite لـ Forced Browsing — القفز من المرحلة 2 للمرحلة 4 متجاوزًا الدفع.

Connection Pool DoSإنشاء استعلامات SQL ضخمة متعددة في وقت واحد لاستهلاك كل الاتصالات في الـ Pool — في ASP.NET الحد الأقصى 100 اتصال ومهلة 30 ثانية

04الـ Web API والـ Webhooks

Web API

الـ Web API واجهة برمجية توفّر خدمات ويب لتطبيقات جانب العميل لاسترداد وتحديث بيانات من مصادر متعدّدة عبر الإنترنت. يُوصَل إليها عادةً عبر HTTP.

نوع الـ APIالشرح
SOAP APIبروتوكول اتصال يُمكِّن التفاعل بين منصّات مختلفة عبر XML وHTTP — يُولِّد ويُعدِّل ويحذف السجلات
REST APIأسلوب معماري يعمل كوسيط اتصال بين الأنظمة عبر الويب
RESTful APIREST مبني على مبادئ REST وبروتوكولات HTTP — يستخدم PUT وPOST وGET وDELETE. يجعل التطبيقات مستقلّة لتحسين الأداء والـ Scalability

Webhooks

الـ Webhooks HTTP Callbacks مُعرَّفة من المستخدم تُطلَق بناءً على أحداث مُحدَّدة (مثل تلقّي تعليق أو Push لكود). تُسمّى أحيانًا "Reverse APIs" — تُبلِّغ التطبيقات الأخرى بآخر المعلومات فور حدوثها بدون حاجة لاستعلام دوري.

منهجية اختراق Web API

1
تحديد الهدف

تحليل HTTP Headers وMessage Formats (JSON لـ REST، XML لـ SOAP). API Enumeration بأداة Kiterunner — أداة متقدّمة للمسح السياقي لـ APIs.

2
تحديد Attack Surface

فحص API Metadata (Paths وParameters وMessage Formats) — REST يستخدم Swagger وRAML وAPI-Blueprint، SOAP يستخدم WSDL/XML-Schema. لو لا Metadata، مراقبة وتسجيل الاتصال بين API والعميل.

3
تنفيذ الهجمات

Fuzzing (Fuzzapi)، Invalid Input Attacks، Malicious Input Attacks، Injection Attacks، Insecure SSL Config، IDOR، Insecure Session/Authentication Handling، API DDoS Attacks.

Secure API Architecture — أفضل الممارسات

  • استخدام HTTPS عبر SSL/TLS
  • استخدام Tokens مُولَّدة من السيرفر كـ Hidden Fields للتحقّق من الطلبات
  • تعقيم البيانات والتحقّق السليم من الإدخال
  • IP Whitelisting للوصول للـ APIs
  • Rate Limiting لتحديد عدد طلبات API في وحدة الزمن
  • API Gateways لمصادقة الحركة والتحكّم والتحليل
  • MFA وبروتوكولات مصادقة مثل AppToken وOAuth2 وOpenID Connect
  • SOAP APIs بدلًا من REST التقليدي لأمان مدمَج أقوى
  • WAF مع TLS/SSL لتأمين APIs

أفضل ممارسات تأمين Webhooks

  • HTTPS بدلًا من HTTP لحماية البيانات أثناء النقل
  • مشاركة Authentication Secrets (HTTP Basic Auth) لجميع Webhooks
  • Webhook Signing للتحقّق من بيانات ESPs وباستخدام Constant Time-Compare
  • تتبّع event_id لتجنّب المعالجة المزدوجة غير المقصودة (Replay Attacks)
  • الـ Firewall يرفض Webhook Calls من مصادر غير مصرَّح بها غير ESPs
  • Rate Limiting على Webhook Calls في Web Server

الخلاصة العامة للموديول

الموديول ناقش مفاهيم الـ Web Application وWeb Services وطبقات الـ Vulnerability Stack الست، وأكثر من 25 نوع هجوم، ومنهجية الاختراق الكاملة في 13 مرحلة. ثم تطرّق لمفاهيم Web API وWebhooks ومنهجية اختراقها، وأنواع اختبار الأمان (SAST وDASTوFuzzing) وأنواع الترميز والإجراءات المضادة.

$ cat ./module14_summary.txt
  • الـ Web Application بتشتغل على 3 طبقات: Client (Presentation) ← Business Logic ← Database — كل طبقة نقطة هجوم محتملة
  • XXE هو SSRF على مستوى XML Parser — ينجح لما المحلّل مُهيَّأ بشكل خاطئ ويقبل كيانات خارجية
  • MarioNet خطير لأن العدوى تستمرّ بعد إغلاق الصفحة عبر Service Worker API
  • Password Reset Poisoning يستغل Host Header لتحويل رابط الإعادة لسيرفر المهاجم
  • Connection Pool DoS يستهدف قاعدة البيانات بـ 100 استعلام بطيء (30 ثانية+) في وقت واحد لاستهلاك كل الاتصالات
  • Webhooks هي "Reverse APIs" — Push عند الحدث بدلًا من Poll دوري — وتأمينها يستلزم HTTPS وSigning وevent_id tracking
  • SAST يحلّل الكود الثابت (White-box)، DAST يختبر Runtime (Black-box)، وFuzzing يضخّ بيانات عشوائية لكشف ثغرات الحافّة

الـ Web Application ليست مجرّد موقع — هي نظام طبقات. كلّ طبقة من الـ 6 (Vulnerability Stack) تقدّم نافذة مختلفة للمهاجم: من SQL Injection في قاعدة البيانات، لـ XSS في منطق الأعمال، لـ Banner Grabbing في السيرفر. الدفاع الحقيقي يبدأ بفهم هذه الطبقات والتحقّق السليم من كل مدخل في كل مستوى.
