01نظرة عامة على استطلاع السحابة

ليه استطلاع السحابة مختلف

الاستطلاع التقليدي بيعتمد على فحص IPs وفحص الخدمات وإيجاد منافذ مفتوحة. استطلاع السحابة بيضيف أسطح هجوم جديدة تمامًا.

1واجهات مزوّد السحابة (APIs) متاحة بشكل عام
2الموارد عندها أنماط تسمية متوقَّعة يمكن تخمينها
3Metadata الحساب بتتسرّب من خلال سلوك الـ API نفسه
4الموارد العامة ممكن تكشف البنية الداخلية للمؤسسة

AWS واحدة من أكثر منصات السحابة انتشارًا — وهي التركيز الأساسي لهذا الموديول.

منظوران للتعداد

خارجي
بدون مصادقة
معلومات عامة بس — بدون أي وصول لحساب سحابي: سجلات DNS، WHOIS، ملكية الـ IP، روابط عامة، أدوات متصفح الشبكة، وتعداد الـ Subdomains.
داخلي
بعد المصادقة
بيانات اعتماد أو مفاتيح API متاحة — تفاعل مباشر مع واجهات المزوّد لتعداد الموارد: تحليل IAM، AMIs العامة، Snapshots، وS3 Buckets.
مبدأ أساسي

التعداد دايمًا تكراري — أي وصول أو بيانات اعتماد جديدة لازم تبدأ دورة استطلاع جديدة.

02استطلاع DNS والدومين

البداية من دومين واحد

  • المعلومة الوحيدة المعروفة: الدومين الأساسي فقط (مثلًا BadGlitch.io)
  • الخطوة 1 — استعلام سجلات NS: بيكشف مين بيدير DNS الدومين. نمط AWS Route 53: *.awsdns-*.com / .org / .net / .co.uk — ده لوحده بيؤكد استخدام AWS
  • الخطوة 2 — WHOIS على دومين الـ Name Server: بيؤكد الملكية لأمازون عبر معلومات المسجّل

البصمة التقنية — أوامر عملية

dns fingerprinting
# استعلام سجلات NS:
nslookup -type=NS badglitch.io
# → ns-XXX.awsdns-XX.com

# تحويل الدومين لـ IP:
nslookup badglitch.io
# → 52.x.x.x (نطاق AWS العام)

# Reverse DNS lookup:
nslookup 52.x.x.x
# → ec2-52-x-x-x.compute-1.amazonaws.com

# WHOIS على الـ IP:
whois 52.x.x.x | grep -i 'amazon\|aws'
# يؤكد: AMAZON-EC2
نمط EC2

نمط Reverse DNS الخاص بـ EC2: ec2-X-X-X-X.compute-1.amazonaws.com — بيؤكد وجود جهاز افتراضي على AWS EC2.

تعداد الـ Subdomains

  • كل Subdomain ممكن يمثّل خدمة أو بيئة مختلفة — بيئات Dev/Staging/Internal غالبًا سيئة الإعداد
  • الطرق: DNS brute-force بـ Wordlists، سجلات Certificate Transparency (crt.sh)، محركات البحث (site:domain.com)
  • الأدوات: amass، subfinder، dnsx، وضع DNS في gobuster
  • كل Subdomain جديد بيعيد تشغيل عملية البصمة من الأول

03استطلاع الدومين الخاص بالخدمات

كيف تُنشئ خدمات AWS روابط متوقَّعة

الخدمةنمط الرابط
S3 Bucket<bucket-name>.s3.amazonaws.com
S3 Bucket (بديل)s3.amazonaws.com/<bucket-name>
CloudFront<id>.cloudfront.net
EC2ec2-X-X-X-X.compute-1.amazonaws.com

اكتشاف أي رابط خدمة بيكشف الخدمة السحابية المستخدَمة، وأنماط التسمية بتفضح عادات التنظيم الداخلية — معرفة اسم Bucket واحد بتساعد في تخمين أسماء تانية.

أدوات المتصفح للاستطلاع

  • فتح الموقع الهدف وتشغيل DevTools (F12) → تبويب Network → إعادة تحميل الصفحة
  • كل طلب مورد ظاهر: JavaScript، CSS، صور، خطوط، استدعاءات API — بما فيها الموارد من دومينات خارجية زي S3 buckets
  • ركّز على الطلبات لـ *.s3.amazonaws.com — بتكشف أسماء الـ Buckets، ومسار الرابط غالبًا بيكشف البنية الداخلية للملفات

أخطاء إعداد S3 Bucket

أخطاء شائعة وخطيرة
  • تفعيل سرد المحتويات (Bucket Listing) → سرد كل الأوبجكتس جوه الـ Bucket
  • ACL مفرط في الصلاحية → أي حد يقدر يقرأ ملفات خاصة
  • بدون تشفير → البيانات مكشوفة بشكل نصي

حتى من غير صلاحية سرد: رسائل الخطأ بتؤكد وجود الـ Bucket من عدمه — 403 يعني الـ Bucket موجود لكن الوصول مرفوض، و404 يعني الـ Bucket مش موجود أصلًا. جرّب أنماط زي company-dev، company-backup، company-staging.

أدوات اكتشاف Buckets آلية

  • GrayhatWarfare.com — بحث عن S3 Buckets المكشوفة علنًا بالكلمة المفتاحية، عبر عدة مزوّدين سحابيين، بدون مصادقة
  • S3Scanner — أداة CLI لتعداد الـ Buckets، بتجرّب تباديل مختلفة من الأسماء وبترجّع حالة عام/خاص/متاح
أنماط تسمية للتجربة

company-name، companyname-public، companyname-static، companyname-assets، companyname-backup، companyname-dev، companyname-staging، companyname-prod — وماتنساش فحص Azure Blob وGCP Storage أيضًا في بيئات Multi-cloud.

04الاستطلاع عبر API

طريقتان للتفاعل مع AWS

  • Web Console (GUI): واجهة إدارة بالمتصفح، محتاجة اسم مستخدم + كلمة مرور + MFA
  • AWS CLI (API برمجي): وصول سطر أوامر لكل خدمات AWS، محتاج Access Key ID + Secret Access Key
أسلوب المهاجم

إنشاء حساب AWS خاص بالمهاجم نفسه للحصول على بيانات اعتماد API شرعية، واستخدامها للاستعلام عن واجهات المزوّد السحابي واكتشاف الموارد اللي المؤسسات الهدف شاركتها علنًا. ده إجراء قانوني — استعلام APIs عامة من حسابك الخاص.

aws cli setup + sts verification
aws configure --profile attacker

AWS Secret Access Key: ...

aws --profile attacker sts get-caller-identity
# {

AMIs العامة — كنز استخباراتي

  • AMI = Amazon Machine Image، قالب جهاز افتراضي لإطلاق EC2 instances. المؤسسات بتنشئ AMIs مخصّصة ببرامج وإعدادات مثبّتة مسبقًا
ليه AMIs المخصّصة خطيرة لما تكون عامة

ممكن تحتوي بيانات اعتماد مضمَّنة (مفاتيح API، كلمات مرور في ملفات الإعداد)، تكشف المكدّس البرمجي والبنية الداخلية، وتاغاتها بتفضح أسماء المشاريع والبيئات والفرق. حقل الـ owner بيكشف Account ID صاحب الـ AMI مباشرة.

discovering public amis + snapshots
aws --profile attacker ec2 describe-images \
  --filters 'Name=name,Values=*badglitch*' --owners self amazon

aws ec2 describe-images --executable-users all \
  --filters 'Name=name,Values=*company*'

# OwnerId: 123456789012  ← Account ID الهدف!
# Name: badglitch-web-prod-2024

# بعد معرفة الـ Account ID:
aws ec2 describe-snapshots --owner-ids 
aws rds describe-db-snapshots --snapshot-type public

Snapshots الـ EBS نسخ احتياطية لأقراص كاملة — Public EBS snapshot يعني أي حد يقدر ينشئ Volume منه ويوصّله. Snapshots الـ RDS نسخ قاعدة بيانات كاملة في لحظة معيّنة — Public RDS snapshot يعني أي حد يقدر يسترجع قاعدة بيانات منه.

05الحصول على Account ID عبر S3

الفكرة الجوهرية

الهدف: اكتشاف Account ID الخاص بـ AWS بتاع الهدف من غير أي وصول مباشر. الحيلة: شروط IAM policy تقدر تتحقّق من Account ID مالك المورد — وAWS بيُقيِّم الشرط ده قبل منح الوصول. استجابة السماح/الرفض بتكشف هل الشرط كان صح أو غلط.

نظام الصلاحيات كـ Oracle

اختبار "هل الـ Account ID بيبدأ بـ 0؟" → رفض. اختبار "هل بيبدأ بـ 1؟" → سماح → الرقم الأول هو '1'! تكرار العملية لكل رقم تالي → إعادة بناء الـ ID الكامل (12 رقم).

1
إنشاء مستخدم IAM مقيَّد

في حساب المهاجم الخاص — مستخدم جديد بدون أي صلاحيات افتراضيًا.

2
تحديد S3 Bucket عام

إيجاد Bucket قابل للقراءة علنًا وتابع للمؤسسة الهدف.

3
إنشاء IAM Policy شرطية

منح صلاحية محدودة (s3:ListBucket) فقط لو Account ID مالك المورد بيطابق بادئة معيّنة.

4
ربط الـ Policy واختبارها

محاولة سرد الـ Bucket — النجاح = الشرط اتحقق = الرقم صح.

5
التكرار لكل رقم

توسيع البادئة رقم رقم — اختبار كل الأرقام العشرة لكل موضع.

6
إعادة بناء الـ ID الكامل

بعد 12 تكرارًا — رقم الحساب الكامل المكوَّن من 12 رقم بيظهر بالكامل.

7
استخدام الـ ID لاستطلاع إضافي

البحث عن AMIs وSnapshots وهويات IAM باستخدام الـ Account ID المكتشَف.

ليه التقنية دي خفيّة جدًا

كل الإجراءات بتحصل جوه حساب المهاجم نفسه — إنشاء المستخدمين والسياسات والاختبار كلها عمليات داخلية. اللوجات بتتسجّل في CloudTrail بتاع المهاجم بس، وحساب الهدف ميشوفش غير وصول عادي للـ Bucket العام. مفيش تنبيهات Brute-force — حجم الطلبات قليل جدًا، والعملية ممكن تُؤتمت بالكامل.

06تعداد مستخدمي وأدوار IAM

كيف يسرّب تحقّق IAM principal البيانات

AWS بيتحقّق من صحة IAM principals قبل حفظ سياسات الموارد. المهاجم بينشئ Resource policy بتمنح وصول لـ ARN مستخدم مُخمَّن — لو الـ Policy اتحفظت بنجاح، المستخدم ده موجود فعلًا في الحساب الهدف؛ لو ظهر خطأ "Invalid principal"، المستخدم مش موجود. ده عمليًا تعداد Brute-force عبر استجابات الـ API — بدون أي محاولات تسجيل دخول، فمفيش Lockouts أبدًا.

أسماء IAM شائعة للتجربة

  • عامة عالية القيمة: admin، administrator، root، devops، developer، cloudadmin
  • sysadmin، backup، security، auditor، support، helpdesk
  • cicd، jenkins، terraform، ansible، packer، github-actions
  • billing، finance، readonly، monitor، loganalytics
  • أنماط خاصة بالمؤسسة: firstname.lastname، f.lastname، company-admin

تعداد الأدوار (Roles) — أهداف أعلى قيمة

الأدوار غالبًا عندها صلاحيات أعلى من المستخدمين — مصمَّمة للخدمات والتطبيقات والوصول عبر الحسابات، وغالبًا بتشمل صلاحيات بمستوى أدمن. نفس تقنية التحقّق بتنطبق: تخمين ARN الدور في Resource policy، وAWS بيتحقّق هل الدور موجود فعلًا. أسماء أدوار مستهدَفة: Admin، Backup، SecurityAudit، PowerUser، DevOps، CICD، CrossAccount، Lambda-Exec.

سوء إعداد AssumeRole

لو دور مكتشَف بيثق في حسابات خارجية، المهاجم يقدر ينادي sts:AssumeRole ويستلم بيانات اعتماد مؤقتة للحساب الهدف — وده بينقل الوضع من استطلاع لـ اختراق أولي فعلي. إعداد سيئ: ثقة في aws:* (كل الحسابات)، وحتى الثقة في حسابات محدَّدة من غير شرط ExternalId فيها خطورة.

خصائص التخفّي

كل التعداد بيحصل في حساب المهاجم الخاص — إنشاء السياسات واختبارها مبيولّدش أي لوجات في حساب الهدف. الاستثناء الوحيد: انتحال الدور (Role Assumption) الناجح — استدعاءات AssumeRole بتظهر في CloudTrail الخاص بالهدف.

07صلاحيات IAM وتحليل السياسات

تقييم بيانات اعتماد مخترَقة

أول أمر لازم تنفّذه مع بيانات اعتماد مخترَقة: aws sts get-caller-identity — بيكشف Account ID، UserID، وARN الكامل. مثال: arn:aws:iam::123456789:user/support/clouddesk-plove — المسار "/support/" بيلمّح لغرض الحساب، وحتى عادات التسمية بتكشف الصلاحيات المحتملة.

كيف تُورَّث الصلاحيات في IAM

  1. سياسات مضمَّنة (Inline): مدمجة مباشرة في المستخدم — خاصة بهوية معيّنة
  2. سياسات مُدارة مرفقة: سياسات مستقلة مربوطة مباشرة بالمستخدم
  3. سياسات المجموعات: المستخدم بيرث كل صلاحيات كل مجموعة هو عضو فيها — وده غالبًا بيتم تجاهله وبيكون واسع جدًا
mapping user permissions
aws iam list-groups-for-user --user-name clouddesk-plove
# GroupName: support

aws iam list-attached-group-policies --group-name support
# SupportUser (AWS Managed Policy)

aws iam get-policy-version \
  --policy-arn arn:aws:iam::aws:policy/SupportUser --version-id v8
# يعرض كل الأفعال المسموحة!
SupportUser — للقراءة فقط لكنه خطير

بيمنح وصول للقراءة فقط عبر خدمات AWS كتيرة جدًا — كل عمليات Get*، Describe*، List* على كل خدمة تقريبًا. مينفعش ينشئ أو يعدّل موارد — لكن قيمته الاستطلاعية هائلة: رسم خريطة البنية التحتية بالكامل، قراءة الإعدادات والشهادات وسياسات التوسّع، وتحديد أهداف للتصعيد. القراءة فقط ≠ غير مؤذٍ في أمن السحابة.

09معالجة البيانات بـ JMESPath

ليه JMESPath مهم

AWS CLI بيرجّع البيانات بصيغة JSON — غالبًا ضخمة جدًا، مئات أو آلاف الأوبجكتس في الاستجابة الواحدة. JMESPath لغة استعلام مخصّصة لمستندات JSON، مدمجة في AWS CLI عبر --query لفلترة وإعادة تشكيل البيانات من جهة العميل.

ميزة أساسية للتخفّي

--query من جهة العميل — بدون أي استدعاءات API إضافية. --filter من جهة السيرفر — بيقلّل البيانات المرسلة من AWS. مع بعض: أقل استدعاءات API، أقصى استخبارات.

jmespath practical examples
# استخراج كل أسماء المستخدمين:
aws iam get-account-authorization-details \
  --query 'UserDetailList[].UserName'

# إيجاد المستخدمين المرتبطين بـ admin:
aws iam get-account-authorization-details \
  --query 'UserDetailList[?contains(UserName,`admin`)].UserName'
# النتيجة: ["admin", "cloudadmin"]

# المستخدمين مع السياسات المرفقة بيهم:
aws iam get-account-authorization-details \
  --query 'UserDetailList[].[UserName,AttachedManagedPolicies[].PolicyName]'

# معالجة ملفات JSON محفوظة محليًا:
jp -f full_iam_dump.json 'expression'

10التعداد الآلي بـ Pacu

ما هو Pacu؟

  • إطار استغلال AWS مفتوح المصدر، طوّرته Rhino Security Labs مخصّص لتقييمات AWS
  • منظَّم في موديولات تستهدف خدمات AWS محدَّدة، مبني على جلسات (كل تقييم بيتخزّن منفصل)
  • بيستورد بروفايلات AWS CLI الموجودة، وقاعدة بيانات داخلية بتخزّن كل البيانات المُجمَّعة
CloudTrail — القلق الأساسي للكشف

AWS CloudTrail بيسجّل كل نشاط API افتراضيًا — كل أمر aws بتشغّله = إدخال لوج في حساب الهدف (اسم الفعل، IP المصدر، User Agent اللي ممكن يكشف awscli أو boto3 أو pacu، الوقت، والمعاملات). Pacu بيشغّل استدعاءات API كتير وبسرعة = طفرة واضحة في CloudTrail، وUser Agent بتاعه مميَّز في اللوجات.

--تحليل النتائج ومسارات التصعيد

البيانات الخام مجرد بداية — القيمة الحقيقية في التحليل. بعد أي تعداد (يدوي أو آلي)، ركّز على:

  • مستخدمين فيهم "admin" في الاسم — غالبًا صلاحيات عالية
  • مجموعات مرفق بيها سياسات قوية
  • صلاحيات Wildcard (Action: '*'، Resource: '*')
  • سياسات بتسمح بـ iam:CreateUser، iam:AttachUserPolicy، iam:AddUserToGroup
من دومين واحد بدون وصول، وحتى مسار تصعيد كامل جوه حساب AWS الهدف

الخلاصة العامة للموديول

الموديول ده غطّى تعداد بنية AWS السحابية من اسم دومين واحد بدون أي وصول، مرورًا باستغلال سلوك IAM كـ Oracle، ووصولًا لتعداد وتحليل صلاحيات IAM الكامل يدويًا وآليًا عبر JMESPath وPacu.

$ cat ./module22_summary.txt
  • استطلاع السحابة تكراري — أي وصول أو بيانات اعتماد جديدة لازم تشغّل دورة تعداد جديدة
  • تحليل DNS، وبحث WHOIS، وReverse DNS تقدر تحدّد بصمة البنية السحابية قبل أي مصادقة
  • أدوات متصفح المطوّر بتكشف روابط خاصة بالخدمات — أسماء S3 buckets، نقاط نهاية CDN، وبوابات API بتفضح عادات التسمية
  • AMIs العامة وEBS snapshots ممكن تحتوي أسرار مضمَّنة وملفات إعداد وتفاصيل بنية داخلية
  • شروط IAM policy ممكن تُستغَل كـ Oracle لـ Brute-force رقم حساب AWS الهدف رقم برقم
  • AWS بيتحقّق من IAM principals قبل تطبيق سياسات الموارد — السلوك ده بيسرّب هل المستخدمين والأدوار موجودين فعلًا
  • بيانات اعتماد منخفضة الصلاحية مخترَقة لسه ممكن تمكّن استطلاع واسع لو عندها صلاحيات IAM للقراءة فقط
  • JMESPath بيسمح بفلترة استجابات API الضخمة محليًا — استدعاءات API أقل = مخاطر كشف أقل
  • Pacu بيؤتمت تعداد IAM والخدمات — لكن الأتمتة ضجيجها عالي وقابلة للكشف عبر CloudTrail
  • مبدأ Least Privilege هو الدفاع الأساسي — الصلاحيات المفرطة لسه السبب الجذري لمعظم اختراقات السحابة

كل تقنيات الموديول ده مبنية على فكرة واحدة: سلوك واجهات AWS نفسها بيسرّب معلومات حتى لما الهدف من التصميم رفض الوصول. المختبر اللي بيفهم إن كل استجابة — سماح، رفض، أو حتى رسالة خطأ — بتحمل معنى، هو اللي بيحوّل واجهة سحابية مغلقة لخريطة كاملة للحساب الهدف.

Professional Mindset

في الـ Engagement الحقيقي: ابدأ دايمًا بالاستطلاع الخارجي الصامت (DNS، WHOIS، S3 المكشوف، أدوات المتصفح) → استخرج أي Account ID متاح عبر S3 أو AMIs العامة → لو عندك بيانات اعتماد ولو منخفضة الصلاحية، نفّذ get-account-authorization-details فورًا وحلّلها أوفلاين بـ JMESPath → استخدم الأتمتة (Pacu) بس لما السرعة أهم من التخفّي، وراقب أثرك في CloudTrail. وثَّق كل خطوة، حتى الفاشلة.
